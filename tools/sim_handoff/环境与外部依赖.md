# 环境、外部下载与配置顺序

本清单为接收端准备，尚未在接收电脑安装或验收。Docker／WSL已由SHELL报告配置，不要求重装。模板不是完整离线镜像，不包含已配置好的WSLg显示或PX4二进制。

## 用户态与架构

| 配置 | 用途与限制 |
|---|---|
| Ubuntu18.04 amd64＋ROS1 Melodic＋Gazebo Classic9＋PX4 v1.13.3 | 与当前RK的ROS代际对齐；Python2 ROS与Python3 YOLO须另作兼容设计；软件源／镜像可得性在接收端核实 |
| Ubuntu20.04 amd64＋ROS1 Noetic＋Gazebo Classic11 | 已有环境时的PC候选；核对PX4 v1.13.3工具链、Gazebo插件及旧路径，不能把换版本当作已验收 |
| ARM64 RK运行栈 | 仅目标板参考；不在PC仿真安装GPIO上电／NPU服务或复用ARM64动态库 |

ROS2和现代Gazebo另算迁移，不直接覆盖本项目ROS1／Classic基线。现有仿真脚本默认Noetic，实际环境须显式设置ROS_DISTRO。

## 包内模板

- `Dockerfile.base`：在ROS基础镜像上补通用8包编译所需的系统／ROS依赖，默认Melodic；可通过ROS_IMAGE参数换为经过核对的Noetic基础镜像。模板未在发送端构建，软件源签名／可用性以实际结果为准。
- `apt-common.txt`、`apt-ros-common.txt`：通用编译项；后者`${ROS_DISTRO}`由构建模板展开。
- `apt-simulation.txt`：Gazebo／SLAM／bridge运行依赖清单，独立安装并检查可得性；缺二进制包时使用锁定官方源码，不默默跳过后称全链完成。
- `requirements-yolo-cpu.txt`：PC CPU核验候选，仅供独立Python3.10+进程；不要直接装进Melodic Python2 ROS或用它覆盖系统cv_bridge。目标Python版本不同，应先形成实际兼容锁定。

在handoff目录可参考：

```bash
docker build -f Dockerfile.base -t shell-uav-sim:melodic-build .
```

只在接收端执行，先核对基础镜像。构建成功仅表示基础编译镜像生成，不表示PX4、Gazebo渲染或YOLO ROS完成。未提供特权／设备透传运行命令，也未自动挂载真实硬件；显示socket和工作卷按实际WSL／Docker环境配置。

ROS、Gazebo、PX4和Cartographer等第三方源码／完整安装包不在本包中。训练原ZIP、训练检查点和历史原始训练日志未随包；导出模型和精选报告已齐。原始数据ZIP完整随包，只读使用，不需要先做训练。

PX4获取参考（Linux终端，已有checkout则先检查，不覆盖）：

```bash
git clone --branch v1.13.3 https://github.com/PX4/PX4-Autopilot.git PX4-Autopilot
git -C PX4-Autopilot submodule update --init --recursive
git -C PX4-Autopilot rev-parse HEAD
git -C PX4-Autopilot submodule status --recursive
```

这是下载源码，不会构建或启动仿真。项目脚本默认从`$HOME/PX4-Autopilot`查找，可通过PX4_ROOT显式指定实际目录。

## 构建与运行检查

在完成基础镜像和工作卷安排后，将`project/src`置于新catkin工作空间，先source实际ROS，再以`catkin_make -j2 -l2`建立干净构建。相同源码支持catkin_tools时也可使用；不要混用同一工作空间的两套构建输出。

当前八包的非JetsonC++目标预期为：location_node、tfmini_test、rplidarNode、rplidarNodeClient、servo_controller_node、rescue_mission_node、ego_trajectory_controller_node、ego_planner_2d_node、gazebo_simulation_vehicle_node、px4_sensor_rig_node、usb_cam_node。先按当前CMake核对名称；构建统计还包含库／消息／测试。Jetson条件目标ssd_detection_node在PC被跳过是预期边界，不是YOLO已完成。

运行gtest只覆盖已有算法／生命周期等单元测试，不代替仿真。不要把location_node／tfmini_test或servo_controller_node当作只读环境检查，它们可能打开真实接口。

当前完整模型审计工具`verify_yolo_delivery.py`默认需要原训练交付ZIP且执行整体audit；该ZIP未打包，不能直接以其main作为环境测试。接收端应先独立加载包内ONNX，按已纠正的解码函数建立小样，再实现ROS节点；不要为了通过审计伪造缺失checkpoint／原ZIP。对应历史验收报告已经随快照提供。
