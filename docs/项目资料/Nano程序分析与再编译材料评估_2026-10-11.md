## 再编译需要验证的具体事项

1. **评估电脑 WSL＋Docker 构建适配。** 原 Nano 独立工作空间的建议已取消。后续核对电脑架构、GPU、系统/ROS 与 Jetson 专用依赖，确定各目标的构建方式和覆盖；现有 AArch64 库不能直接视为已适配电脑容器。本轮只调整文档，不执行环境配置或构建。
2. **固定依赖选择。** 原缓存使用 `/usr/lib/aarch64-linux-gnu/cmake/opencv4` 与 `/usr/bin/python2`；系统同时有 OpenCV 3.2/4.1 及多套 Python。新版配置搜索结果不能默认为与原构建相同。CUDA/NVIDIA 头文件的链接布局也应按 Linux 原件处理。
3. **确认实际生成所有必需目标。** [SSD CMake](../../src/ssd_detection/CMakeLists.txt) 对视觉依赖使用 `QUIET`，找不到时跳过 C++ 检测节点，整个工作空间仍可能构建结束。验收要检查 `ssd_detection_node` 确实重建，并核对生成消息、链接库和其他机载节点，不能只看总退出码。
4. **六包重编译与外部库重建分别安排。** 六包默认链接既有 jetson 库，不要求先重建 ROS/CUDA 全套。若之后修改 `jetson-inference`，其 CMake 默认 `BUILD_DEPS=YES` 会调用依赖安装脚本，需要另行控制构建选项；当前只读分析没有执行它。

当前范围不包含“把所有第三方 ROS 库从源码重建”或“在新系统完全离线重装”。安装文件和版本清单支持链接与环境核对，但不是这些第三方仓库和全部离线安装包的替代品。

## 分析范围的实际限制

- 导航 README 提及的 `gc_2026_sim`、部分检查/标定工具没有在当前机载工程中发现。它们影响原仿真/测试流程的完整复现，不是六个机载包默认编译的关键源文件。默认 C++ 编译也不要求补齐原训练数据。
- 静态审计已发现视觉输入内存接口需要后续核对：项目把普通 `cv::Mat` 指针传入 `detectNet::Detect`，所保存的外部头文件标注输入应位于 CUDA device memory。这是运行层面的验证事项，目前没有实测为故障，也不属于缺少编译材料。
- 编译通过不等于识别、定位或控制效果合格。当前未执行构建、推理、舵机或飞行节点；静态分析可以继续独立于硬件进行。
