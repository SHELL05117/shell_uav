## 1. 当前建议与“是否必须编译系统”

**先用适用于ProD的厂商Debian 10 BSP建立硬件/NPU基准，再做ROS兼容试验。现在没有证据表明必须从零编译整套系统，也不建议第一步自行移植Ubuntu。** 固件包能启动、NPU运行正常，与项目六个ROS包能构建是不同检查点。

SHELL提出“官方只支持Debian 10”。检索结论是：有官方Debian 10固件及维护转向的依据，但不能理解成芯片只能运行Debian，或2026年仍享有持续系统维护。

- [官方2019年ProD Debian 10正式发布](https://t.rock-chips.com/forum.php?mod=viewthread&tid=1121)证明该型号有官方固件；帖子已明确早期下载地址失效，应转资料下载入口。
- [官方管理员2020年D/X Debian 10 V2.0公告](https://t.rock-chips.com/forum.php?mod=viewthread&tid=2385)记录Debian 10.6和RKNN 1.5.0；它是历史版本证据，不是本次指定安装包。
- [官方RKNN维护说明](https://t.rock-chips.com/forum.php?mod=viewthread&tid=964)说明旧阶段建议切换Debian 10、ProD Fedora不再提供RKNN在线更新。旧[Startup页面](https://t.rock-chips.com/en/wiki.php?filename=Getting_Start/Startup)仍写ProD预装Fedora 28＋Android，属于旧出厂说明，不能取代后来的固件公告。
- [当前官方Downloads入口](https://t.rock-chips.com/en/wiki.php?filename=Downloads/Downloads)按ProD单列Linux镜像、烧写工具、硬件资料和源码。首次通过网页工具未能读取网盘清单；后续沿公开页面引用的JavaScript请求链，以匿名只读请求成功取得ProD Linux目录，见下表。**包内容、实际软件版本和SHA256仍待完整下载核验**；不可把ProX或普通RK3399镜像刷到ProD。

## 2. 系统、ROS与原程序的关系

现有源码入口为 `../../src`，有location、navigation_2d、ego_planner_2d、rplidar_ros、servo_control、ssd_detection六包。Nano基线为Ubuntu 18.04/Melodic；视觉C++目标依赖CUDA、jetson-inference/detectNet，不能搬到Mali GPU或RK NPU继续运行。现有TensorRT engine不可复用。

[ROS REP-3原始文件](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0003.rst)列Melodic主要对应Ubuntu 18.04、Python 2，Debian推荐平台是Stretch；Noetic推荐Debian Buster、Python 3。故Debian 10不应直接混装Ubuntu Bionic软件源安装Melodic。

| 路线 | 价值 | 主要工作与当前选择 |
|---|---|---|
| 厂商Debian 10＋原生ROS1 Noetic兼容试验 | 保留板级驱动，Buster在Noetic历史目标内 | **优先进行小规模构建试验**：从ROS基础、消息与单个C++节点开始，核对Python 3、cv_bridge、OpenCV、Cartographer/Ceres/Abseil、MAVROS依赖。Buster/arm64二进制仓库能否获取须实查，必要时固定源码构建；推荐平台不等于今天可直接apt安装全部包 |
| 厂商Debian 10＋ARM64 Ubuntu 18.04/Melodic容器 | 尽量保留旧ROS用户态 | 第二候选。先确认厂商内核的cgroups/namespaces/容器支持及可用Docker版本，再验证网络、串口、I²C和相机。NPU采用宿主独立进程或严格匹配库的容器；容器不会补齐宿主NPU驱动。不能直接复制PC的amd64镜像 |
| 厂商BSP＋自行制作Ubuntu rootfs | 用户态更接近旧工程或便于新ROS | 后备专项。保留匹配的启动链/内核/设备树并逐一验证Mali/RGA/NPU、网络、USB、I²C；需要可回退镜像与sysroot。尚无本型号可直接使用的Ubuntu固件核验证据 |
| 在Debian 10源码强行维持Melodic | 尽量少改旧代码 | 不作首选；不在其Debian推荐版本内，Python/依赖补丁成本需与Noetic迁移实测比较 |
| Fedora 28旧镜像 | 历史恢复、理解旧文档 | 不作新开发首选；RKNN维护转向Debian的依据见上文 |

**本轮选择的是验证顺序，尚未锁定最终ROS版本。** Noetic也已于2025年结束ROS官方支持；Debian 10的Debian LTS于2024-06-30结束（[Debian公告](https://www.debian.org/News/2024/20240615)）。它们可用于有边界的旧硬件兼容验证；后续长期维护方案需另评估，不把“2026年最新系统”与“旧NPU可用”混为同一条件。

只有遇到缺驱动、设备树未启用目标接口、启动链不匹配等实际问题，才针对性重编内核/设备树。修改应用代码另建分支；不在Nano建立rebuild空间，也不将板端独立重编整个项目作为默认部署流程。目标产物可由电脑通过匹配的ARM64工具链＋sysroot生成；依赖构建需要时单列专项。

## 3. 到货后先做的版本采集（尚未执行）

先脱离飞控、舵机和无人机线束，用符合板卡规格的已验证电源、网线和显示/调试方式检查。不要先覆盖卖家提供的可启动系统；记录实物型号、PCB版本、系统和NPU演示结果，再判断是否刷机。保存原固件/恢复资料或必要配置不等于要求整盘备份旧Nano。

在板上终端可采集以下只读信息；缺少命令时如实记录，不为采集而盲目升级系统：

```sh
cat /etc/os-release
uname -a
uname -m
tr -d '\000' </proc/device-tree/model
free -h
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
findmnt -no SOURCE,FSTYPE,OPTIONS /
ip -br link
ip -br address
ip route
ls /dev/i2c-*
```

Debian再读取 `dpkg-query -W '*rknn*' '*rockchip*'`，可能有无匹配提示；运行库/API/驱动版本以NPU官方示例输出补齐，不能只看pip包版本。6GB按采购标称为CPU 4GB＋NPU 2GB，Linux `free`可用内存不会等于6GB。

将真实输出、固件包哈希和日志存入 `验证记录/` 的当天独立目录。记录可以出现真实工具时间戳，不将其改成工程归属日期。

## 4. 可以不用TF卡：eMMC烧系统，程序适配后部署

**可以把系统和项目运行文件放在32GB eMMC上，无需依赖TF卡启动。** 这是该板的标准存储用途；不等于把Nano的卡镜像或旧可执行文件直接复制后就能运行。

两件事分别做：

1. **烧写系统**：匹配ProD的启动文件、内核、设备树、根文件系统及分区配置，通过烧写工具写入eMMC。
2. **部署程序**：在可启动的Linux上安装依赖，传入源文件/匹配ARM64构建产物、新RKNN模型、配置和标签。通常用局域网SSH/SCP/SFTP，不需每改程序就重新刷系统。

[官方硬件Wiki](https://t.rock-chips.com/en/wiki.php?filename=Board_Guide/TB-RK3399ProD)明确eMMC为系统盘。应用部署到eMMC的文件系统是工程实施方式；启动根分区与完整项目验收仍需到货实测。

### 接口与工具

| 接口 | 作用 |
|---|---|
| Type-C **USB OTG**＋支持数据传输的USB线接Windows PC | 烧写/恢复连接；不是把Type-C当作已确认的板卡供电入口，也不自动提供Nano式USB网卡 |
| 独立DC输入 | 按本板电源规格供电；降压模块及极性核验见[供电评估](RK板供电引脚与顶板材料评估_2026-10-21.md) |
| Micro-USB DEBUG | 板载USB转串口的调试通道，与Type-C烧写口不同；厂商硬件文档列调试波特率1500000，接线/串口参数按到货板和手册核对 |
| 千兆网口/已验证Wi-Fi | 日常远程登录、传文件、ROS数据通信 |

[官方Flash Images指南](https://t.rock-chips.com/en/wiki.php?filename=Getting_Start/Flash_Images)给出Windows驱动、AndroidTool与LOADER/MASKROM流程。执行前必须拿到同包的镜像、分区配置和烧写说明，记录来源及SHA256；本轮未生成带固定地址的烧写命令。

后续操作顺序：安装对应USB烧写驱动 → 保持独立稳定供电，用数据线接OTG → 按官方手册用Recovery配合Reset进入Loader → 工具正确识别设备 → 导入该固件包附带的Linux配置并检查路径/分区 → 写入 → 保留成功及错误日志 → 重启并检查系统。若原系统为旧MBR分区、需要迁移到官方GPT镜像，官方指南要求使用Maskrom；恢复故障也可能需要该模式。先核对现有分区、固件手册与具体板卡操作，不一律套Loader流程；不要随意短接焊盘、擦除Flash或套别板地址。[厂商社区教程](https://t.rock-chips.com/forum.php?mod=viewthread&tid=4313)可辅助理解界面，其发帖者为注册会员，证据等级低于官方Wiki。

**完成标准：** 断电后移除TF卡，再上电能从eMMC独立进入目标系统；用 `findmnt`、`lsblk`、对应 `/sys/block/mmcblk*/device/type` 区分MMC与SD，并保留启动日志。不能预先写死eMMC是 `/dev/mmcblk0`；必要时检查U-Boot启动配置，排除仍依赖TF中的引导文件。接着验证持久化文件、剩余空间、网络和NPU，再部署项目。32GB实际可用少于标称，训练集/大量rosbag不宜长期占满系统盘。

## 5. 加入局域网：先网线DHCP，再Wi-Fi，再地址保留

**SHELL答复后确定的使用方式：** 路由器品牌为 **TP-Link**，具体型号暂不清楚；沿用“路由器不接互联网，只建立局域网，电脑通过SSH连接无人机”的方式，并希望rk板继续使用 **192.168.1.102**。这是网络需求和历史使用方式，不表示新板已获得该IP。具体LAN网段/掩码、新板MAC和旧Nano的保留项仍待到货时读取。

SSH、SFTP和同一局域网中的ROS/监看通信不依赖路由器WAN上网。软件包、固件、训练依赖等下载可另由有网电脑准备，再通过局域网或存储介质导入；“设备运行在离线局域网”与“开发阶段需要取得软件包”分开安排。

推荐首次接路由器LAN口，让路由器DHCP分配地址；电脑接同一路由器，关闭客户端/AP隔离。板上 `ip -br address` 与 `ip route`、路由器客户端清单应能相互印证。没有显示器时可用调试串口或路由器清单发现地址；Type-C不保证提供USB网络。

若系统运行NetworkManager，先用 `nmcli device status`、`nmcli connection show` 检查实际设备和连接。官方硬件资料列板载Wi-Fi为2.4GHz 802.11b/g/n；先用兼容的2.4GHz网络，不假设支持5GHz或WPA3专用网络。接天线、驱动和实物无线模块仍须核对。

```sh
# 以下是NetworkManager存在且正在管理无线设备时的操作示例
nmcli device wifi list
nmcli --ask device wifi connect '替换为实际SSID'
ip -br address
ip route
```

SSID替换后执行；`--ask`交互输入口令，不把Wi-Fi密码写入文档或命令历史。不确定由NetworkManager、systemd-networkd还是ifupdown管理时，先查清，避免两个网络管理器接管同一个网口。上述方法依据[NetworkManager官方示例](https://networkmanager.dev/docs/api/latest/nmcli-examples.html)，旧版选项以本机 `nmcli --help` 为准。

### 路由器固定分配IP（DHCP地址保留）

1. 记录**当前实际接入接口**的MAC：有线与Wi-Fi各有自己的MAC，不能混填；使用随机/克隆MAC时先确认连接重启后仍稳定。
2. 在路由器“DHCP服务/地址保留/静态租约”等界面，将该MAC关联一个同LAN网段且未占用的地址，保存并让连接重新取得租约。板上通常仍使用DHCP自动取址。
3. SHELL已确认希望沿用历史 `192.168.1.102`；先读取当前路由器LAN地址和掩码，确认该IP位于其子网内且未被占用，再处理旧Nano的地址保留项，以新板实际接入接口MAC重新绑定。若原网段确为 `192.168.1.0/24` 可按该网段安排；不能仅凭旧IP推定掩码必为 `/24`。**不直接宣称rk板已经取得此地址。** DHCP池、保留规则和菜单以实际路由器为准。
4. 将连接的永久MAC和最终IP一并记录。无线和有线若都启用，分别规划地址及默认路由，避免把两个接口随意设成同一IP。

[TP-Link官方地址保留说明](https://www.tp-link.com/us/support/faq/182/)解释MAC与保留地址的关系；品牌已由SHELL确认为TP-Link，具体型号仍未确认，此文仅给通用对应流程，不能指定其菜单截图。手工在板上设静态IP是另一种方式，本项目优先路由器保留，减少网关/DNS冲突。

### 登录与验收

登录账户以新系统实际创建/提供者为准，不沿用Nano的 `jcfh`。检查SSH服务及22端口；若Debian未安装服务，确认软件源可用后安装 `openssh-server`，再记录实际服务状态。改变预置默认凭据后使用局域网SSH；不为ROS调试开放公网端口。

最低验收：板到网关可达 → 电脑到板可达 → SSH成功 → 文件传输校验通过 → 板/路由器重启后仍获保留地址 → 分别记录网线和Wi-Fi表现。再测ROS话题/桥连接的带宽、时延和断线恢复；SSH通过不能证明ROS跨机通信通过。ROS1还涉及Master地址及主机互访，Docker Desktop/WSL2的网络方式需按[另一电脑提示词](另一台电脑_虚拟环境与Gazebo配置提示词_2026-10-21.md)单独验证。
