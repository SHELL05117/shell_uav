## 3. 两个工具、三个 img 各是什么

`.img` 只是常用文件后缀，不能凭后缀判断它是整套固件、某个分区，还是 Docker 镜像。本轮已读取文件头、封装清单和文件系统中的选定公开元数据。

| 文件 | 实际检查结果 | 应用位置 |
|---|---|---|
| `DriverAssitant_v5.13.zip` | 包含 `DriverInstall.exe` 和 Rockusb Windows 驱动 | Windows 电脑，用于识别处于烧写模式的 RK 设备 |
| `RKDevTool_v3.30_for_window.zip` | 包含 `RKDevTool.exe`、`AFPTool.exe`、`RKImageMaker.exe` 等 | Windows 电脑上的烧写／封装工具；不是板上 ROS 软件 |
| `boot_linux.img` | 67,108,864 字节，64 MiB；ext 家族文件系统，内有 `extlinux/Image`、`extlinux.conf` 和多个 `toybrick*.dtb` | 启动分区，提供 Linux 内核及描述板上硬件的设备树等；**它不等于 U-Boot 本身** |
| `rootfs.img` | 6,442,450,944 字节，6 GiB；Ubuntu18.04 ARM64 根文件系统 | Linux 启动后的 `/`，容纳系统程序、库、配置，以及以后安装的 ROS 和项目依赖 |
| `TB-RK3399ProD-Ubuntu-18.04-update.img` | 1,374,261,720 字节，约 1.28 GiB；外层 `RKFW`，内层 `RKAF` | 供 RK 工具解析的统一升级包，不是原始整盘镜像或 Docker 镜像 |

驱动只是让 Windows 能与烧写模式设备通信；RKDevTool 负责发送固件。二者均不会替板上的 Ubuntu 安装 ROS。本轮没有运行压缩包里的可执行程序。

## 4. 学长第4条逐句解释，以及到底替代哪个文件

**“从官方包里提取了 uboot 这些”**：Linux 用户态不是板卡启动所需的全部内容。还需要初始化与引导组件、固件分区信息和适配硬件的内核／设备树。U-Boot 是 Linux 前面的引导程序，负责后续启动。学长表示他把这些配套组件从官方包取出，与自己的系统文件组合；本轮确认包内有这些条目，但没有取得原官方包逐一比对，因此不把组件官方来源和型号兼容性写成已验收。

**“不用单独选了，直接用那个升级固件”**：RKDevTool 的分项下载方式需要分别指定文件及对应分区；统一包已带清单，工具可以解析。对本次包而言，后续计划使用“升级固件”方式选择 `…update.img`，取代逐项选择多个镜像的操作。具体按钮名称、Loader／Maskrom 模式及分区迁移以本板资料和现场状态核对；本轮不是刷写操作记录。[Toybrick 官方烧写说明](https://t.rock-chips.com/wiki.php?filename=%E8%BD%AF%E4%BB%B6%E5%BC%80%E5%8F%91/%E5%BF%AB%E9%80%9F%E5%85%A5%E9%97%A8)

新包内实际列有：

```text
package-file             包内容清单
Image/MiniLoaderAll.bin  下载／初始化用 Loader
Image/parameter.txt      GPT 分区参数
Image/trust.img          配套 Trust 固件
Image/uboot.img          U-Boot
Image/boot_linux.img     Linux 启动分区
Image/rootfs.img         Ubuntu 根文件系统
```

**所以它在使用方式上替代的是“原来的 boot_linux＋rootfs 以及其他配套引导文件的分项刷写组合”，并非只替代 `boot_linux.img` 或只替代 `rootfs.img`。** 原先两个文件是分开的部件，现在打成一个包含它们的包。新旧文件都保留用于追溯；若按新包方案刷写，不再凭猜测混搭旧 rootfs 或另一个版本的启动组件。

**“压缩完善了一下，这个小一点”**：本轮不是只看文件大小作推测。

- 新包内 `boot_linux` 的 SHA256 与旧 `boot_linux.img` 完全相同，确认这部分逐字节一致。
- 新包内 rootfs 为 **1,297,825,792 字节，约 1.21 GiB**，其文件系统声明容量也为该值；旧 rootfs 为 6 GiB。可确认根文件系统镜像已缩小，而不是仅换了文件名或套了一个 ZIP。
- 两份 rootfs 的 `/etc/os-release`、`/etc/lsb-release`、`/etc/debian_version`、`/var/lib/dpkg/status`、`/bin/bash`、`/usr/bin/python3` 的哈希逐项一致。这支持保留了所查系统内容的判断，**没有对全文件树做一致性认证**；无法仅凭结果还原学长用了哪些缩容命令。
- `parameter` 中可见 GPT 和 `rootfs:grow`；这不证明首次启动一定会把文件系统自动扩到整块 eMMC。到货后仍要以 `lsblk`、`findmnt /`、`df -h /` 核验分区与文件系统空间。

**“有个 rkimagetool，按官方工具链弄的，应该没问题”**：意思是他找到了固件封装工具，并认为生成格式符合工具要求。本地 `RKFW/RKAF` 格式与内部清单确实可解析；“可解析”尚不能证明供电、具体 PCB、DDR／eMMC、驱动、NPU 和开机稳定性均已通过。工具名本身也不能证明他实际采用了哪一版实现。

## 6. “Wi-Fi 要改 netplan”是在说什么

本次 rootfs 确实有 `/etc/netplan/01-toybrick.yaml`，并登记了 `netplan.io`。学长是在说：把 **RK 板这套 Ubuntu 中的网络配置文件**改为你所用无线网的配置，再让系统应用；与 Windows 的 Wi-Fi 设置及 Docker 容器联网不是同一处设置。

下面只是字段示意，`wlan0` 不是已核实的设备名，SSID／密码均为占位文字；到货后按 `ip -br link`、`iw dev` 取得真实无线接口名，并沿用原配置实际使用的 renderer，不盲目覆盖整个文件：

```yaml
network:
  version: 2
  wifis:
    wlan0:
      dhcp4: true
      access-points:
        "替换为无线网络名称":
          password: "替换为无线网络密码"
```

`wifis` 表示无线设备，`access-points` 填无线网络，`dhcp4` 表示从路由器取 IPv4 地址。实际修改前备份原配置；在本地控制台或保留有线连接的条件下检查语法并试用当前版本支持的 `netplan try`／应用方式，避免改完无线配置就失去唯一的 SSH 通道。不能只改这个片段而忽略原来的有线、renderer 或其他配置。[Netplan 官方示例](https://netplan.readthedocs.io/en/stable/examples/)

本轮只记录文件存在，没有读取或保存 Wi-Fi 密码。沿用 SHELL 已确定的 TP-Link 离线局域网方案，板端取 DHCP 地址后，在路由器按实际无线 MAC 做地址保留，核对无冲突再安排 `192.168.1.102`。网线和 Wi-Fi 的 MAC 不同；加入离线局域网后可以 SSH，但安装依赖还需要另行取得软件包。

## 7. 为什么不能把这几个 img 塞进 Docker 直接跑

这里有三个不同层次：

```text
电脑端：Windows → Docker Desktop 的 WSL2 Linux 内核 → amd64 Ubuntu/ROS 容器
板卡端：RK 引导固件 → RK Linux 内核/设备树 → ARM64 Ubuntu → ROS/项目
仿真端：电脑 ROS 任务 → MAVROS → 电脑上运行的 PX4 SITL ↔ Gazebo 世界/传感器
```

Docker 容器使用宿主的 Linux 内核，Ubuntu 容器主要提供 Ubuntu 用户态软件；它不会用 `boot_linux.img` 替换 WSL2 内核，更不会因此得到 RK 的外设和 NPU。当前电脑是 amd64，固件用户态是 ARM64，现成二进制也不相通。[Docker 多平台说明](https://docs.docker.com/build/building/multi-platform/)

技术上可另做 ARM 用户态提取、仿真和容器制作，但那需要额外转换与兼容处理；直接 `docker load` 这些固件并不能启动系统，`docker import` 也不是把裸分区镜像还原成完整板卡。QEMU 用户态模拟可解决部分指令集运行问题，仍不会自动复制整块 RK 的驱动、NPU或真实时序，不作为当前 Gazebo 路线。

当前可继续复用已安装的一套 Docker Desktop，使用其 WSL2 后端，无需为了这件事先再安装第二套 Docker Engine或独立 WSL Ubuntu。Docker 官方说明它可以直接从 Windows 终端使用，不要求先安装指定用户发行版。[Docker WSL2 说明](https://docs.docker.com/desktop/features/wsl/)
