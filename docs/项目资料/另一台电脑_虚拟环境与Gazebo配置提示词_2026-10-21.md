## 1. 本次推荐及依据

**先保留 Windows，使用一套 Docker Desktop、WSL2 后端完成通用 ROS 编译；Gazebo 放在下一阶段单独验收。** 这是延续 SHELL 在10月13日提出的使用偏好，并根据10月19日至21日改用 RK3399ProD 的决定调整目标。电脑上的旧 ROS 环境用于理解和复现导出程序；RK 板的系统选择、ARM64 编译及 NPU 驱动属于另外的验收范围。

| 要解决的事 | 本次选择 | 尚不能据此宣称的结果 |
|---|---|---|
| 阅读、编译现有 ROS1 源码 | `linux/amd64` 的 Ubuntu18.04／ROS Melodic 兼容容器；冻结依赖与镜像摘要 | RK 板系统或 ARM64 程序已配置完成 |
| 项目假消息、离线图像、回放 | 先验证消息、任务和规划，不依赖真实外设 | 真实飞控、I²C、舵机或飞行动力学已通过 |
| PX4 SITL 与 Gazebo | 候选固定为 PX4 `v1.13.3`、Gazebo Classic9、MAVROS1.x，先默认单机，再项目场景 | 安装 Gazebo 就已有消防任务仿真 |
| Gazebo 窗口和渲染 | 实际验证 GUI、OpenGL 渲染器、传感器与实时倍率；WSLg／容器图形链路需逐项配置 | `nvidia-smi` 或 CUDA 样例成功即代表 Gazebo GPU 加速成功 |
| RK 板视觉 | 单独的、与 RK3399Pro 驱动匹配的 RKNN 转换及板端推理环境 | RTX 的 CUDA／TensorRT 环境可以运行 RK NPU 或复用 Nano engine |

Docker 官方说明：Windows 终端可直接使用 Docker Desktop 的 WSL2 后端，**无需预装独立 Ubuntu 发行版**；也应避免同时维护另一套 WSL 内 Docker Engine。若后续确实需要 Linux 终端、编辑工作副本或建立可核验的 WSLg 显示接入，再增加一个工具用 WSL 发行版；它不代表项目迁移到该发行版内的新版 ROS。[Docker WSL2 后端说明](https://docs.docker.com/desktop/features/wsl/)

Microsoft 官方说明 WSL2 可运行 X11／Wayland GUI，并通过相应 Windows 显卡驱动支持加速 OpenGL；Docker 官方的 `--gpus` 路线主要说明 NVIDIA 计算资源接入。这两条能力需要分别测试，旧 Bionic 容器的图形库、显示套接字和设备映射也须实际匹配。[WSL GUI 官方说明](https://learn.microsoft.com/en-us/windows/wsl/tutorials/gui-apps)；[Docker GPU 官方说明](https://docs.docker.com/desktop/features/gpu/)

传统 VMware／VirtualBox 等 Linux 虚拟机也可以作为 Gazebo 的运行候选，但其虚拟显卡、OpenGL 能力、CPU／内存和场景负载决定实际表现，不能仅凭主机有3060Ti就推定客户机能直接使用该显卡。当前16GB条件下，不建议同时常驻传统虚拟机和 Docker 的 WSL2 环境；若图形链路持续遇阻，再比较已安装虚拟机的实测渲染与原生 Linux 方案。此处是工程取舍，未在该电脑测试。

旧组合的用途是减少导出源码的初次适配变量，**不是新 RK 板操作系统的既定选择**。ROS Melodic 生命周期为2018年5月至2023年5月，Gazebo Classic 已在2025年1月结束支持；2026年配置时应先确认旧依赖仍可获得，再固定可复现环境，不能承诺当年的脚本现在直接执行必然成功。[ROS 官方 REP-3 源文件](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0003.rst)；[Gazebo Classic 官方公告](https://classic.gazebosim.org/)

### 阶段0：先核对这台机器

先给出最多一小组只读检查，分别标注“Windows PowerShell普通权限”或确需管理员的操作。检查 Windows版本、CPU和逻辑核心、物理内存与可用内存、C／目标数据盘余量、固件虚拟化、WSL版本与发行版列表、Docker客户端与服务端状态、NVIDIA驱动和显存。

可依据环境使用 `Get-CimInstance`、`Get-Volume`、`wsl --version`、`wsl --status`、`wsl -l -v`、`docker version`、`docker info`、`nvidia-smi`。命令不存在或WSL未启用时如实记录；不要把查询失败当成硬件不支持，也不要直接运行安装脚本来代替检查。

核对当时 Microsoft／Docker 官方支持条件和下载地址，按当前机器现状选择适配版本。不要默认 Windows版本符合要求。已有工作环境先读取配置；涉及BIOS、重启或关闭所有WSL实例时说明影响，并在SHELL可操作时安排。

### 阶段1：一套 Docker Desktop 与最小容器

1. 保留 Windows。准备 WSL2功能和 Docker Desktop 的 Linux容器／WSL2后端，先不要求额外 Ubuntu发行版。通过 Windows终端操作 Docker即可。若检测到独立 Docker Engine，先解释是否冲突并保留其数据，再安排迁移，不直接卸载或清空。
2. 我只有16GB内存。先按CPU能力取最多4个逻辑处理器、WSL内存上限6GB、swap2GB、构建并行2作为起点；这是初始预算，不是性能保证。读取现有 `%UserProfile%\.wslconfig` 后合并所需键，不覆盖其他设置。Docker数据盘位置根据余量安排；不要直接移动、删除运行中的虚拟磁盘。
3. 先验证 Docker客户端能连接服务端、容器架构为 `linux/amd64`，并运行一个简单容器。记录实际 Docker／WSL版本；暂不装 GPU工具链或Gazebo。容器可启动只能记为“基础容器通过”。
4. 第一套项目容器优先评估 `Ubuntu18.04 + ROS Melodic`。检查候选官方基础镜像tag、平台和digest是否还能拉取，检查旧ROS／Ubuntu源、签名密钥与依赖是否可用，再提供确定的 Dockerfile和启动命令。不要给我一个未经核实的旧镜像tag就宣布可用。
5. ROS发行版、系统、Python、OpenCV和编译器须成套。不要直接把Melodic的Python2绑定与Python3检测脚本混在一起；若做Python3视觉，单列兼容验证或使用清晰的消息进程边界。
6. 首次可从Windows只读挂载输入资料，复制到Docker命名卷中的Linux工作副本，再在卷内编译；输出日志导出到Windows可见目录。若已有工具用WSL发行版，也可在其Linux文件系统建立副本。避免在Windows共享挂载目录上复用旧构建树；持久数据要落卷，容器移除后仍保留，另提供导出和重建方法。
7. 旧仓库证书、签名或包地址遇错时，查官方存档／快照与版本固定方法，不关闭包签名校验，不混用不同Ubuntu发行版软件源，不为绕过依赖直接升级整个项目到ROS2。旧依赖确实不可获得时，先保存失败证据并列出可执行替代方案。

### 阶段2：按源码核对编译覆盖

先读实际CMake，不凭包名判断是否构建完整。当前已分析的目标清单为：

| 包 | 需要分别记录的目标 |
|---|---|
| location | `location_node`、`tfmini_test` |
| rplidar_ros | `rplidarNode`、`rplidarNodeClient` |
| ego_planner_2d | `ego_planner_2d_node`，以及 `bspline_opt`、`path_searching`、`grid_map_2d`、`plan_manage` 四个静态库 |
| navigation_2d | `rescue_mission_node`、`ego_trajectory_controller_node` |
| servo_control | `servo_controller_node` |
| ssd_detection | 自定义消息、Python脚本；C++ `ssd_detection_node` 为Jetson依赖条件目标 |

电脑阶段预期核查8个非Jetson可执行目标；旧Jetson C++视觉是第9个条件目标。缺 `jetson-inference`／CUDA时 CMake可能跳过第9个节点。即使catkin退出0，也只能按实际产物说“8个通用目标编译通过、Jetson目标未覆盖”，不能说全工程完整重建。Cartographer、MAVROS、ROS桥等工作空间外依赖的安装／构建版本也要另表记录。

I²C和串口代码能在x86编译，不代表容器拥有实际设备。编译完成后检查产物架构、主要动态链接与消息生成；保留构建日志、镜像digest、依赖版本和源码提交／差异。若出现需要修改构建文件的地方，先说明问题，并只在开发副本分支做最小适配。

电脑阶段不复用Nano ARM64的TensorRT engine，不安装JetPack来让RTX模拟Jetson。CPU视觉、RTX视觉和RKNN板端视觉是三种分别验收的后端；RTX的CUDA可用不意味着RK NPU可用。RK3399Pro专用模型转换后续使用匹配的独立旧RKNN工具环境，不与本阶段ROS容器随意混装Python依赖。

### 阶段3：回放与仿真准备

先运行隔离的假消息／录制数据测试，再接Gazebo。源码已有OpenCV DNN的Python检测入口，但预处理、标签、输出协议和Python／cv_bridge仍需核验；使用旧模型或CPU后端通过，只能证明对应输入和后端的结果。

不要默认运行项目的真实 `navigation_2d.launch` 或 `location.launch`。先逐层检查启动链，它们可能打开真实I²C、舵机、雷达或飞控并发送控制设定值。`is_simulation=true`不能证明所有硬件被隔离。新建明确的仿真配置：只连SITL UDP、使用仿真传感器和机构ACK、隔离ROS Master；初期不挂USB、串口或I²C设备，不使用全量特权容器。

初期让ROS Master、MAVROS、任务节点和SITL在同一容器／同一明确网络空间运行，减少跨主机TCPROS地址问题。若拆容器，提供并验证名称解析和各节点可回连地址；只开放11311不足以解决ROS1全部通信。Windows QGC／Lichtblick需要的UDP／WebSocket端口根据实际运行配置单独映射；不要假设Docker的 `--network host` 与原生Linux一致，也不要把生产局域网中的真实飞控端点带入仿真。

### 阶段4：Gazebo 与 PX4 SITL，另行验收

先用官方v1.13文档和固定源码tag检查候选：`Ubuntu18.04 / ROS Melodic / Gazebo Classic9 / PX4 v1.13.3 / MAVROS1.x`。它们已属旧版本，先验证依赖可获得性与构建，再决定实施。不执行主分支一键脚本把固定环境改为最新版。

基线来源入口为 `https://github.com/PX4/PX4-Autopilot` 的 `v1.13.3` tag及其递归子模块。安装完成后，候选启动入口为 `make px4_sitl gazebo`；必须先对该tag的构建目标和模型检查，不把该命令作为依赖安装命令。

1. 首先核验显示方案。Docker Desktop不自带可直接使用的Linux桌面；若要用WSLg，检查宿主WSL／驱动、实际显示套接字、环境变量和设备映射，并在容器内验证最小GUI和OpenGL。若因此需要工具用WSL发行版，请说明它的用途，再增加一份发行版；不安装第二套Docker。
2. 分别记录 Windows `nvidia-smi`、容器CUDA样例、容器OpenGL renderer、Gazebo窗口与传感器结果。发现 `llvmpipe` 等软件渲染器时如实记录，不把窗口可见写成RTX加速。无GUI物理仿真可先推进，但相机和GPU激光等仍可能需要渲染上下文，不能一概称headless无需图形能力。
3. 若旧容器图形链路难以工作，先保留已通过的编译环境，给出具体阻塞、可复现实验与替代方案。比较现有虚拟机的实际3D能力或原生Linux；不要直接重装Windows／改磁盘分区。现代Gazebo／ROS2迁移另列范围，不当作旧工程的无缝替换。
4. 先跑默认单架Iris与简单世界，验证仿真时钟、PX4／MAVROS连接、模式和基本设定值；再添加二维激光、相机、下向高度、对应TF和仿真舵机ACK。默认Iris不会自动产生本项目的 `/scan`、卡片图像或真实机构反馈。
5. SLAM阶段区分Gazebo真值与Cartographer估计；控制、图像、检测、规划消息使用一致的 `/clock`／`use_sim_time` 策略。先验证坐标方向、原点、yaw、传感器外参和高度来源，避免将二维定位的z=0当作飞行高度。
6. 单架、简单场景、图像先5～10FPS，逐层测“控制”“控制＋SLAM/EGO”“再加检测／JPEG”。每层记录内存、换页、CPU／GPU、real-time factor、话题频率、最大间隔与延迟；依据实测再调整资源，不能保证16GB可同时流畅运行全链。
7. 优先复现已发现风险：停止检测后旧框是否继续计数、相机／投放ACK丢失或错序、无路径／旧轨迹、返航终点、OFFBOARD失流、降落请求被拒绝。保存SITL ULog、ROS日志、场景／模型、种子与判定；这些通过也不代表RK板推理、电气或飞行已验收。
