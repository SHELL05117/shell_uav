仅在没有获得IP时，使用下面配置。先用`ip -br link`取得实际网卡名；示例eth0／wlan0须替换为实际名称。先在本地显示器操作，`sudo vi /etc/netplan/01-toybrick.yaml`，修改现有配置中对应接口，保留其他必要配置，不在多个文件重复定义同一接口的静态地址／网关。已有renderer保持；以下为networkd示例。

### 已填YAML但wlan0仍为DOWN的最短处理

**SHELL此前补充：** 原Debian10曾能用`nmcli device wifi list`列出附近Wi-Fi，当时本节恢复命令尚未尝试；该未执行状态已由下方新照片更新。此前扫描成功属于原系统证据，支持当时无线硬件／驱动／扫描链可工作，不代表新Ubuntu已联网。nmcli是NetworkManager客户端，本次Ubuntu固件未预装该管理器，当前继续沿用networkd，不为此切换管理方案。

若希望像原来先看附近热点，可在当前Ubuntu用已内置的iw扫描：

```bash
sudo rfkill unblock wifi
sudo ip link set wlan0 up
sudo iw dev wlan0 scan | grep -E 'SSID:|signal:'
```

能列出SSID说明当前Ubuntu也具备扫描能力，但尚不代表认证和DHCP成功；接着执行下方Netplan生成／应用步骤。若命令报错，保留第一个错误，按该结果定位，不把上一版方案记为已失败。[nmcli官方说明](https://networkmanager.dev/docs/api/latest/nmcli-examples.html)

针对上述renderer为networkd的配置，在板上本地终端逐条执行；任一步报错先保留该输出，不直接认定板卡或驱动损坏，也不为此重刷系统：

```bash
sudo rfkill unblock wifi
sudo ip link set wlan0 up
sudo netplan generate
sudo systemctl start systemd-networkd
sudo netplan apply
```

等10–20秒再看：

```bash
iw dev wlan0 link
ip -4 address show dev wlan0
```

应看到Connected to及路由器分配的inet地址。只修改YAML不会自动完成应用；`netplan generate`检查并生成配置，`netplan apply`才应用。`ip link`的管理标志UP和后面的运行状态不是同一件事：flags里有UP、同时显示NO-CARRIER／state DOWN，可能是无线还未关联，而非接口未开启。[内核运行状态说明](https://docs.kernel.org/networking/operstates.html)

本轮已直接只读核查FULL-v2包内rootfs，wpasupplicant、rfkill、iw、wireless-tools均登记已装，对应核心命令存在，systemd-networkd启用链接存在；未登记NetworkManager或isc-dhcp-client。因此当前不要求先联网安装nmcli／dhclient，也不额外启动第二套无线认证进程。[镜像核查证据](../验证记录/RK无线联网核查_2026-10-23/无线工具与网络服务核查.json)

仍未连上时，只回传下面输出及上面首先报错的命令；不贴包含Wi-Fi密码的YAML或生成的wpa配置：

```bash
rfkill list
ip link show wlan0
sudo journalctl -b -u netplan-wpa-wlan0.service -u systemd-networkd --no-pager -n 40
```

- RF-kill错误：先看rfkill。Soft blocked可用上述unblock解除；Hard blocked不能仅靠该命令解除，应核对板级无线使能／驱动实际日志，不凭此假定存在实体开关。[内核rfkill说明](https://docs.kernel.org/driver-api/rfkill.html)
- YAML报错：先改提示的缩进／字段，不继续装ROS。
- 接口已UP但Not connected：看无线认证服务日志，区分2.4GHz热点不可见、口令／认证方式和服务启动问题。networkd无线需要wpasupplicant，本镜像已存在该组件。[Netplan说明](https://netplan.readthedocs.io/en/stable/netplan-yaml/#properties-for-device-type-wifis)
- Connected但无inet地址：再查DHCP／networkd；已有inet但不能解析域名时才查网关／DNS。

### 最新结果：认证服务不存在，先修配置生成／加载

SHELL新附件IMG_1626.jpeg显示无线rfkill的Soft／Hard blocked均为no；查询netplan-wpa-wlan0.service返回could not be found，其journal为No entries。当前能确认“预期认证服务未被systemd加载”，尚不能区分文件未生成、YAML未读取／选错renderer或systemd尚未刷新，不将其直接归为密码错误。原始FULL-v2镜像的Netplan配置文件名已只读核对为01-toybrick.yaml，但板端编辑后的内容未知。

当前提供明确的修复配置。在板上用现有编辑器新建`/etc/netplan/99-shell-wifi.yaml`，仅配置实际wlan0，并在接口层指定networkd；原有其他接口保留。密码仅在板上填写，不回传：

```bash
sudo vi /etc/netplan/99-shell-wifi.yaml
```

```yaml
network:
  version: 2
  wifis:
    wlan0:
      renderer: networkd
      dhcp4: true
      access-points:
        "SHELL":
          password: "替换为iPhone热点密码"
```

保存后逐条执行；generate或文件检查报错时停在对应位置：

```bash
sudo chmod 600 /etc/netplan/99-shell-wifi.yaml
sudo netplan generate
ls -l /run/systemd/system/netplan-wpa-wlan0.service
sudo netplan apply
sudo systemctl daemon-reload
sudo systemctl restart netplan-wpa-wlan0.service
```

**后续warning接续：** SHELL报告执行原顺序倒数第二行时出现unit file changed on disk，要求daemon-reload。此提示表示systemd需要重新读取已变化的服务定义，不等于已确认认证失败。前序将reload放在apply前，apply可能再次生成unit；当前顺序调整为apply之后reload再restart。已执行到该warning时，只补最后两条daemon-reload／restart，无需重写YAML；随后看关联与IPv4。若仍Not connected，再取服务末25行journal。尚未收到重载／连接成功结果。[systemctl官方说明](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html#daemon-reload)

等15秒后查询`iw dev wlan0 link`及`ip -4 address show wlan0`。生成服务文件出现，才说明配置进入预期networkd无线链；服务能启动和认证成功仍需分别确认。若generate报Updated definition changes device type，说明旧文件把同名wlan0定义成另一类接口，需要从旧文件的ethernets等错误位置移除该wlan0段，保留其他接口，再生成；不要移动或删除整套Netplan目录。其他错误保留原文定位。

本方案同时覆盖路径／.yaml后缀、wifis层级、接口renderer和systemd刷新等候选问题，不代表已确认其中某个就是原始根因。Netplan0.99仅扫描相应目录的*.yaml文件，支持接口级renderer；依据[生成器源码](https://github.com/canonical/netplan/blob/0.99/src/generate.c#L182)及[解析器源码](https://github.com/canonical/netplan/blob/0.99/src/parse.c#L1564)。若服务文件仍不存在，回传上述首先失败的输出；文件存在但未连接，则再取该服务末25行日志。

**已发现的后续安装阻塞：** IMG_1626的板端journal时间仍为2023-03-02，这不是本次工程日期。Wi-Fi取得可上网IP后先执行`sudo timedatectl set-ntp true`，用`date`确认日期／时间已正确，再下载小鱼和安装依赖，避免HTTPS／软件源时间校验失败。尚未执行校时，不把启用NTP等同于已同步成功。

**连接成功后的机制说明：** YAML记录wlan0、SSID、密码和使用的networkd后端；Netplan将其转换成网络配置与无线认证服务定义。systemd是后台服务管理器，daemon-reload让它重新读取磁盘上的服务定义，restart则按已加载定义重启无线认证进程，由该进程与热点关联／认证；之后网络配置服务才能继续申请IP。daemon在Linux中是“守护进程／后台常驻程序”的通用术语，daemon-reload是systemctl的一项管理操作。该机制说明不等于已查明旧YAML的具体失效字段，原文件编辑后内容未取得。结果及边界见[当天日志§16](../../logs/2026-10-23_RK刷写、SSH修复与七包构建.md)。

### 安装菜单中文无法显示时

**SHELL反馈：** 已进入fishros安装过程，菜单中文无法显示，尝试export LANG=en_US.UTF-8及LC_ALL=en_US.UTF-8无效。结合前序tty1现场，优先判断为原生文本控制台的字形显示限制，尚无此轮截图或locale输出，不将其确定为仅缺某个字体包。LANG／LC_ALL控制区域、编码及遵循它们的程序语言，不会为原生控制台增加完整中文字形；另据fishros公开translator.py，语言优先取自公网IP地区，因此单改LANG也未必切换其菜单语言。[内核Unicode说明](https://docs.kernel.org/admin-guide/unicode.html)｜[fishros翻译模块](https://github.com/fishros/install/blob/master/tools/translation/translator.py)

**最快接续：提前使用SSH。** 若当前停在菜单等待输入，可Ctrl+C退出菜单；软件包正在安装时不为换终端中断它。电脑接入与RK相同的SHELL热点／可互通局域网，在板端执行：

```bash

```

```powershell

```

登录后在SSH会话执行：

```bash
export LANG=C.UTF-8 LC_ALL=C.UTF-8
source <(wget -qO- https://fishros.com/install)
```

此时字形由电脑终端渲染；UTF-8用于编码，不承诺将菜单改为英文。C.UTF-8避免依赖尚未生成的en_US locale。SSH成功及中文显示结果待反馈，不将操作方案记为已验收。[Windows Terminal SSH说明](https://learn.microsoft.com/en-us/windows/terminal/tutorials/ssh)

### 历史SSH失败与修复：当前已登录成功

**最新已定位的具体问题：SSH补充配置中的ssh-keygen路径错误。** 新照片IMG_1634.jpeg可见手动sshd -t未打印错误；服务当前EXEC失败目标已变为/usr/sbin/ssh-keygen，顶部还显示openssh-server post-installation失败／dpkg错误1。本段下方重装建议为前一阶段，当前改按本条修复。

当前在板端逐条执行，只改正这一处路径；sed会保留.conf.bak备份，systemd不会将其当作.conf加载：

```bash

sudo systemctl daemon-reload
sudo systemctl reset-failed ssh
sudo systemctl restart ssh
sudo dpkg --configure -a
sudo ss -ltnp 'sport = :22'
```

当前照片中的sshd检查已未报错，本轮不额外重排其他服务配置。dpkg命令用于完成先前失败的安装后配置；任一步出现新错误则停下，保留首先失败的输出。应看到22端口LISTEN，再从Windows用实际IP及实际账户连接；尚未收到本轮修复或SSH成功结果。下方执行文件／密钥排查保留为历史阶段，不再重复重装或仅补密钥。

**SHELL最新实际日志**显示`Failed at step EXEC spawning /usr/sbin/sshd: No such file or directory`和status=203，并最终触发Start request repeated too quickly。当前阻塞发生在执行程序阶段，尚未进入sshd的配置／主机密钥检查；前次仅补密钥未解决当前错误。dpkg的ii登记不能证明现场可执行文件仍完整。[systemd退出码说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Process%20Exit%20Codes)


### 前序线索：镜像未带主机密钥

SHELL会话附件img.png显示openssh-server为ii／7.6p1／arm64，但enable --now ssh报控制进程退出，ss筛选sshd无输出；Windows连接报connection refused。ufw命令不存在只说明该工具未安装，不证明其他防火墙状态，也不能解释为SSH安装包缺失。当前优先恢复服务监听。

助手直接只读核查FULL-v2 rootfs：/etc/ssh只有moduli、ssh_config、sshd_config，没有ssh_host_*主机密钥；服务单元存在ExecStartPre=/usr/sbin/sshd -t，RuntimeDirectory=sshd。此镜像缺失项与启动失败高度吻合，但板端当前主机密钥及具体退出错误仍未直接读取，不将候选原因写成实机已确认根因。[离线核查JSON](../验证记录/RK_SSH核查_2026-10-23/镜像SSH服务与主机密钥元数据.json)

在板端本地终端逐条执行：

```bash
sudo ssh-keygen -A
sudo systemctl reset-failed ssh
sudo systemctl restart ssh
sudo ss -ltnp 'sport = :22'
```

ssh-keygen -A只生成缺失的默认服务器主机密钥，不覆盖已存在的密钥；无需联网、重装软件或发送任何密钥内容。看到LISTEN及:22后，电脑再用实际板端IP连接，例如ssh jcfh@实际IP。enable操作此前已执行，不因启动失败就假定启用未生效。[OpenSSH说明](https://man.openbsd.org/ssh-keygen.1#A)

若restart仍失败，只取`sudo journalctl -b -u ssh --no-pager -n 25`的首个实际错误。若另行使用sshd -t测试，服务停用时systemd可能已移除其RuntimeDirectory，直接测试出现Missing privilege separation directory不能单独当作原始故障；必要时先`sudo install -d -m 0755 /run/sshd`再测试。尚未执行上述修复，未报告监听／SSH登录成功。

```bash
sudo usermod -aG dialout,video "$(id -un)"
if getent group i2c >/dev/null; then
  sudo usermod -aG i2c "$(id -un)"
fi
sudo systemctl enable --now ssh
hostname -I
ip -br link
```

退出当前登录并重新登录，设备组权限才对新会话生效。I²C设备节点是否实际授权给i2c组，以后续设备权限为准；添加组不会自动启用板级I²C或修复设备树。

装完联网包后切回TP-Link正式网络。让路由器正常DHCP分配地址；若要沿用192.168.1.102，在路由器的地址保留中绑定**实际使用网卡的新MAC**，且该地址须属于其LAN网段。未保留前直接用实际分配地址，不强设.102。

Windows PowerShell执行（示例账户toybrick，地址须替换）：

```powershell

```

若已经新建其他账户，改用该账户。只通过SSH操作板上ROS时，不需要先配置Windows／Docker跨机ROS网络。

```bash
  sudo mv /etc/apt/sources.list.d/ros-fish.list /etc/apt/sources.list.d/ros-fish.list.disabled

sudo install -m 644 /tmp/ros-melodic-snapshot.gpg /usr/share/keyrings/ros-melodic-snapshot.gpg
echo 'deb [arch=arm64 signed-by=/usr/share/keyrings/ros-melodic-snapshot.gpg] http://snapshots.ros.org/melodic/final/ubuntu bionic main' | sudo tee /etc/apt/sources.list.d/ros1-snapshots.list
```
