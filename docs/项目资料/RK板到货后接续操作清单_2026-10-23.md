### 2.2 在RK板的Linux终端执行

以下不是Windows PowerShell或电脑Docker内的命令；逐行执行，复制输出即可。缺命令时保留提示，不为采集信息升级系统。

```sh
cat /etc/os-release
uname -a
uname -m
free -h
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
findmnt /
df -h /
ip -br link
ip -br address
ip route
```

看这些结果可以确定原系统与内核、ARM64架构、CPU可见内存、实际根分区及剩余空间、网卡MAC与IP。采购标称6GB为CPU 4GB＋NPU 2GB，Linux可见内存还受保留区等影响，不能要求`free`显示6GB。根分区只有约1.2GB时，先核对分区与文件系统是否扩展，暂不安装大量依赖；不凭设备编号直接扩容或格式化。

若当前是Linux但`ip -br`不被旧版支持，改用`ip link`和`ip address`。若只有Android界面，记录该状态后先取得ADB／调试终端或原系统说明，不把不存在的Linux终端操作记为已执行。

现有ROS另用`command -v rosversion`检查；如果找得到，再执行`rosversion -d`。命令找不到时先检查是否有未加载的现有ROS环境，不能仅凭PATH就断言未安装。

**本步产出：** 上述输出、实物记录及原系统恢复资料来源。必要的原系统配置先本地保存；密码、私钥和含口令的网络文件不发到聊天、不提交Git。只读输出尚未回传，本步未完成。

## 3. 第二轮：让电脑稳定登录，再核验现有NPU

### 3.1 有线网络和SSH

1. 板与电脑接同一路由器，先让DHCP分配地址。使用板端实际IP和实际账户登录，不预设旧Nano的`jcfh`账户或`192.168.55.1`。
2. 核对SSH服务与登录；服务不存在时按原系统的软件管理方式处理，不把Ubuntu安装命令套给未知系统。
3. SHELL已确定希望沿用`192.168.1.102`。确认TP-Link的实际LAN网段、地址空闲及旧Nano保留项后，按新板**实际接入接口MAC**做DHCP地址保留。有线和Wi-Fi的MAC分别记录，不能给两者同时占用同一IP。
4. 验证登录、传输一个无敏感信息的小文件并比对校验值，以及正常重启后重新登录。离线局域网可满足SSH；安装依赖还要另行取得联网或离线软件包。

Wi-Fi放在有线正常之后。只有确认实际系统使用Netplan时才按其现有配置修改，先备份、保留本地／有线登录渠道，不直接覆盖整个配置文件。详见[固件答疑第6节](学长固件说明与Docker仿真答疑_2026-10-22.md)和[系统配网指南第5节](RK板系统迁移_eMMC部署与配网指南_2026-10-21.md)。

### 3.2 NPU先看已有配套，再运行演示

在原系统终端先检查：

```sh
command -v npu_transfer_proxy
ps -ef | grep '[n]pu_transfer_proxy'
```

如果确有这项工具，再执行：

```sh
npu_transfer_proxy devices
```

工具未找到不等于NPU损坏；先核对实际安装位置、系统镜像说明及服务。`devices`用于确认通信识别和USB／PCIe连接方式；**还需运行原系统自带、版本匹配的官方最小模型演示**，记录模型、SDK／驱动／代理版本、输出及错误日志，才能确认该组合可推理。工具与演示未匹配前先保留现状。

RK3399Pro使用第一代RKNN工具链。NPU固件因USB／PCIe通信方式而异，不能用RK3588的Toolkit2、`librknnrt.so`或通用`/dev/rknpu`教程替代本板流程。依据：[Rockchip旧Toolkit](https://github.com/rockchip-linux/rknn-toolkit)、[RK3399Pro专属驱动与代理说明](https://github.com/airockchip/RK3399Pro_npu)。

有配套演示则先留一份运行基准；原系统没有演示或工具时，记录缺项，结合固件资料继续推进，不为补这个基准反复更换系统。

实施时先核对系统、ARM64架构、已有ROS、软件源／签名及实际包候选，再分步处理：

1. ROS基础组件，验证`roscore`及独立测试节点通信，不启动项目任务。
2. MAVROS及所需GeographicLib数据；软件库和地理数据分开验收。
3. Cartographer、TF、OpenCV、Eigen／libi2c等实际构建或运行依赖，按[部署清单](RK3399ProD_Ubuntu18.04部署依赖清单_2026-10-21.md)逐项处理。

## 6. 第五轮：通用模块与视觉分开迁移

### 6.1 通用模块

保留`src/`基线，在独立任务分支准备修改。按消息接口、雷达、定位／Cartographer、EGO与跟随、任务、舵机接口逐目标构建与验证。电脑amd64构建产物不能直接部署到板端；RK产物使用匹配ARM64环境／工具链及依赖构建，依赖来源和构建位置单列，不把板端整套重编设为默认前置。

七包完整声明含10个无条件可执行目标与1个Jetson条件目标；机载迁移可分列仿真和工具。缺Jetson库时CMake跳过检测目标并不代表RK视觉通过。先离线／假消息验证，再分模块台架；当前`location.launch`会连MAVROS和外设，`navigation_2d.launch`默认启用真实舵机，舵机节点初始化即写角度，不能作为普通查看数据入口。`auto_start=false`也不等于取消了这些硬件副作用。

### 6.2 相机与RKNN视觉

相机单独取图→匹配的官方NPU演示→固定测试图片的项目模型推理→类别／框／时间戳一致性→接回ROS检测接口→与定位／规划并行负载测试。旧CUDA／TensorRT／jetson-inference后端必须替换；现有Python后端也不能直接保证在Melodic／Python3／旧OpenCV下运行。先验证实际采集和解释器组合。

首轮NPU基准可按既有评估使用Pro专属YOLOv5s-ReLU演示，后续按同一测试集比较小模型；该演示不具备本项目任务类别，也不保证所需精度或FPS。训练／转换优先放电脑，板端只部署匹配运行库和模型。

**类别纠偏：** 10月21日RKNN评估第4节沿用了version1012的5类SSD／四类目标背景。当前`src/ssd_detection/models/labels.txt`是11类（背景＋9类危险品＋人员），当前技术指南所查ONNX也为11类。旧四类数据是否覆盖当前目标需盘点，最终类别、索引、模型输出和任务`zone`映射逐一对齐，不能直接沿用旧表训练。本轮只核对现有标签和文档，不重跑ONNX解析或推理。

## 7. 供电、接线与顶板可在信息齐全后推进

- 配套适配器启动通过不代表MP1584EN供电支路通过。该模块报告标称输入13.5～28V、输出12V/3A，先独立验证代表性负载、最低带载输入、启动／瞬态及温升，再接RK；原机电源链仍单列核查。
- 先核对实物PCB、1脚方向、排针间距及总线电平。历史图纸的I²C6为3.3V侧候选，I²C7为1.8V侧，不能直接互换；软件总线号也重新映射。TFmini型号／协议／转接线逐根导通核验。
- PCA9685逻辑VCC候选3.3V，舵机V+用独立合格5V支路并共地；TFmini电源按具体型号核对，不因逻辑3.3V就把其供电也改为3.3V。现有舵机“两针”描述按实物追完整电源／地／PWM走线。
- 板已到，可测外形、固定孔、散热器／风扇、接口拔插空间、重量和层间净空。按已确认的LiDAR＋GPS→顶板→RK层叠，先纸样／PLA试装，再据强度与温升测试确定ABS成品。
