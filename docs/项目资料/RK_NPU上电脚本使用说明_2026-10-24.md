## 1. 板端命令

本轮脚本已独立放到RK的`/home/jcfh/rk_npu_power.py`，与本地脚本SHA256一致；原官方RK3399Pro_npu仓库不变。在RK终端执行默认只读检查：

```bash
sudo python3 /home/jcfh/rk_npu_power.py check
```

省略check也是同样的只读检查。输出JSON中的`cold_start_blockers`为空，表示本轮软件预检条件满足；`profile_pcb_revision_verified=false`明确表示程序不能自动识别PCB修订／确认实物走线。check返回0仅表示成功取得报告，不等于已上电或NPU正常。

选择下面的历史ProD控制定义并实际上电，使用显式on：

```bash
sudo python3 /home/jcfh/rk_npu_power.py on --profile prod-20181217
```

该命令会实际写板内NPU电源、复位和时钟控制。`prod-20181217`表示使用哪套已记录的控制定义。本块V1.2实物已按该定义成功运行NPU；尚未取得V1.2图纸或测量各电源轨，不扩展为所有V1.2板卡的电气验收。

需要关闭由此脚本开启的NPU时：

```bash
sudo python3 /home/jcfh/rk_npu_power.py off --profile prod-20181217
```

off只处理本脚本本次启动留下的资源；没有归属记录就不操作，不接管其他脚本已经拉起的NPU。运行中的代理／升级程序／rknn_server须先正常退出，否则off拒绝断电。脚本不执行pkill。

## 2. 控制定义与时序

profile来源是ProD 2018-12-17 V1.0原理图，以及[Rockchip署名npu_powerctrl实现](https://github.com/friendlyarm/linuxsdk-rockchip-buildroot/blob/master/package/rockchip/npu_powerctrl/npu_powerctrl.c)。实物照片为V1.2；尚未取得对应新版图纸或实际电源轨测量。程序的板型、寄存器和空闲检查能够减少误用，不能替代PCB对应关系确认。

| 板内信号 | Linux GPIO号 | 操作 |
|---|---:|---|
| NPU 0.8V使能 | 4 | 第1路，拉高后至少2ms |
| NPU逻辑电源使能 | 10 | 第2路，至少2ms |
| NPU 1.8V／DDR使能 | 11 | 第3路，至少2ms |
| 24MHz参考时钟 | clk_wifi_pmu | 第3路后、第4路前使能 |
| NPU CPU电源使能 | 54 | 第4路，至少2ms |
| NPU 3.3V IO使能 | 55 | 第5路，至少2ms |
| NPU核心电源使能 | 56 | 第6路，至少25ms后释放复位 |
| CPU_RST_NPU | 32 | 全部电源／时钟建立后拉高 |
| CPU_INT_NPU | 36 | 初始化保持低 |
| NPU_INT_CPU／休眠状态 | 35 | 始终作为输入读取 |

另按参考源码使用rk808-clkout2的32k时钟：已有调用者时复用，不增加／减少它们的引用；本脚本从0申请时，关断仅释放本次引用。24MHz的debugfs写入是引用操作，不把数字写入误解成绝对计数赋值。

只允许AArch64、4.4.194和`rockchip,rk3399pro-toybrick-prod-linux`运行标识；核对真实设备树GPIO寄存器地址、NPU时钟复用、24MHz源／门控以及所有目标GPIO未占用、锁存和读回均低。允许未占用的输入或输出低：实板验证发现sysfs unexport会保留输出低方向，不能因此拒绝本脚本正常关断后的重启。已有GPIO占用、混合上电状态或NPU设备时，不提供强制重置／跳过检查选项。

## 3. 结果如何判断

- `power_on_usb_visible`：按此profile执行上电，且在板内05e3:0610／0616集线器的**1号端口**观察到Rockchip USB设备；不同端口或外接RK设备不作为成功证据。它可能只是MaskROM／Loader阶段，**不是推理成功**。JSON中`firmware_loaded_by_script=false`。
- `already_powered_no_reset`：此前由本脚本成功开启，当前输出／时钟状态一致；本次不重复拉低复位、不增加时钟引用。该结果不独立保证当前USB／固件仍健康，查看返回的`npu_usb`。
- 5秒内没有对应USB设备：返回非0，自动按关断顺序回退；可用`--usb-timeout 10`调整等待时间，允许0–30秒。回退后仍需排查实板电压、时序和通道，不能判定硬件已损坏。
- `cleanup_failed`：某项关断／释放失败，保留归属记录并报错；若电源控制未能读回低，不释放这些GPIO。排除明确错误后可重试off，不把回退失败写成已经断电。

上电成功后仍需USB NPU固件启动及代理。以下为配置自动服务之前的手动恢复顺序；启用第6节服务后，使用systemctl统一管理控制链。

```bash
sudo python3 /home/jcfh/rk_npu_power.py on --profile prod-20181217
sudo bash /home/jcfh/npu_runtime_175/rk_npu_boot.sh start
sleep 30
sudo systemctl start shell-npu-proxy.service
npu_transfer_proxy devices
```

[固件辅助脚本](../../tools/rk_npu_boot.sh)锁定已核对的工具哈希、官方仓库提交、四个固件Git blob及唯一板内USB位置，按厂商NPU的RAM启动流程执行。默认check只预检，start要求Maskrom；仅已成功db但后续中断时可用resume（要求Loader）。失败不会自动复位，应先检查实际状态；不向主CPU boot_linux分区写入任何内容。首次Loader曾超时，独立NPU断电／上电后成功，不能承诺每次重启均成功。

固件命令成功不代表NPU内部系统已就绪；本次3秒后测试曾打开接口失败，等待后才成功，上述30秒只作为初始等待，仍须看到设备行并成功推理。代理使用[手动服务](../../tools/shell-npu-proxy.service)，实测active、static，无开机启用段；服务不会负责上电或固件启动。代理更换进程后曾出现官方／六类模型均加载超时，独立NPU重启恢复；只重启代理的恢复性尚未通过。脚本已经powered时，check里的cold_start_blockers为冷启动条件检查，不应单独据此判断运行故障；同时查看ownership、npu_usb和devices。

## 4. 运行归属与失败处理

on／off通过`/run/lock/shell-rk-npu-power.lock`互斥，资源记录为`/run/shell-rk-npu-power.json`，含boot_id、profile、导出GPIO和本次取得的时钟引用。成功上电后保持资源供后续固件／推理使用；正常退出程序不会自动断电。不要在NPU开启时删除该归属文件。

一般异常、SIGINT／SIGTERM会触发启动回退；回退期间不再接受这两类中断。强制SIGKILL、突然断电等不能保证Python清理逻辑执行，不承诺所有情况下自动恢复；跨重启重新检查实际状态，不凭旧记录强制接管。默认不做持久化或开机自启，待真实单模块上电／固件／推理验收后再安排。

## 6. 开机自动启动（SHELL于2026-10-25凌晨授权）

systemd入口为shell-npu.target；启用它会依次拉起shell-npu-power.service、shell-npu-firmware.service、shell-npu-proxy.service。安装副本在/usr/local/lib/shell-rk-npu，root所有，不依赖登录终端或联网下载；仍使用已锁定的/home/jcfh/RK3399Pro_npu固件及/home/jcfh/npu_runtime_175/upgrade_tool。

固件阶段等待板内2207:0019及真实序列号（拒绝0123456789ABCDEF占位值），再等待内部系统10秒；代理阶段有界查询devices并核对板内USB序列号。自动启动只准备NPU，不自动启动YOLO、ROS或任务。失败在journal中报错，不无限重试或偷偷断电复位。单独代理Restart=no，避免代理进程更换后旧连接挂起；需要重新初始化时应重启整个target，并先正常停止使用NPU的程序。

```bash
# 查看当前状态、设备与启动日志
systemctl status shell-npu.target shell-npu-proxy.service --no-pager
npu_transfer_proxy devices
journalctl -b -u shell-npu-power.service -u shell-npu-firmware.service -u shell-npu-proxy.service --no-pager

# 完整重启NPU控制链（先正常结束使用NPU的程序）
sudo systemctl restart shell-npu.target

# 停止并取消以后开机启动
sudo systemctl disable --now shell-npu.target

# 重新开启开机启动并立即运行
sudo systemctl enable --now shell-npu.target
```

停止顺序是代理→固件服务→NPU电源／时钟；最后仍由原上电脚本按归属记录释放，不接管其他程序的GPIO。target停止命令可能先返回，检查power.service已inactive再认为关断完成。debugfs由sys-kernel-debug.mount提供，固件／工具路径由RequiresMountsFor确保已挂载。脚本及unit来源见[自动启动验证报告](../验证记录/RK_NPU自启_2026-10-24/README.md)，此前手动阶段的描述按时间保留。
