# TB-RK3399ProD迁移难点与范围评估

> **后续最终决定：** SHELL已于2026-10-19确认更换为TB-RK3399ProD，重新配置系统并重构视觉识别。下文选型建议与测试资料保留为讨论依据；当前目标与阶段计划以[当天日志末尾](../../logs/2026-10-19_Nano开机故障与换装RK3399ProD.md)及[执行计划](执行计划.md)为准。采购、配置及迁移尚无完成反馈。

日期：2026-10-19。来源：SHELL提供二手商品截图并要求详细解释迁移困难；本报告依据本地导出基线源码及厂商资料，尚未取得候选板实物或完成迁移。现场取消识别后的最新代码仍未回收，不以本地基线替代现场版本。

## 1. 判断与范围

TB-RK3399ProD有迁移可能，项目不是全部重写。大多数ROS任务和规划逻辑属于通用CPU程序；主要不兼容点是原Jetson系统/驱动和CUDA/TensorRT视觉后端，其次是板级外设、软件依赖与实时性能验证。

若目标为尽快恢复已有工程，匹配原机的Jetson Nano模组/载板通常减少适配变量，但仍需重建环境并验证。若团队有可用的RK3399Pro工程、固件及实机经验，迁移成本可明显降低。目前没有足够依据估算完成天数。

## 2. 同为ARM64，只解决CPU指令集的一层

原机核验环境为Ubuntu18.04.6、L4T32.5.2、ROS Melodic、CUDA10.2和TensorRT7.1.3。L4T包含匹配Tegra的内核、设备树和驱动，不能将整张Nano系统卡作为Rockchip启动系统。应先取得支持TB-RK3399ProD实际硬件版本的Linux镜像、恢复工具和驱动，再建立ROS项目环境。

项目C++源码可以重新编译；原机已编译程序和/usr/local库还依赖glibc、OpenCV、ROS及厂商驱动等，不能因为同为aarch64就保证复制运行。部分通用二进制在依赖匹配时可能兼容，应逐项验证，而不是假定全部兼容或全部不兼容。

选择较新Linux用户态时还要处理Melodic、Python和依赖版本；保留旧用户态则要确认相应软件包、内核驱动与工具链。容器可帮助固定用户态依赖，但仍共享宿主内核和实际设备，不能让Mali/NPU执行CUDA代码。

## 3. 视觉后端是最大的明确改动点

原路径：USB图像 → jetson_detector.cpp → jetson-inference detectNet → TensorRT/CUDA → 检测消息 → MissionVision。

`ssd_detection/CMakeLists.txt:67–102`查找并链接CUDA与jetson-inference；`jetson_detector.cpp:40,187`包含detectNet头并创建检测器。这是实际调用，不仅是注释里的Jetson名称。

候选板的GPU为Mali-T860，AI单元为Rockchip NPU；现有TensorRT引擎缓存和CUDA调用不能直接用于它。ONNX模型和标签有复用价值，但仍需可执行后端。

### 3.1 CPU替代路径

源码已有`ssd_detection/scripts/ssd_detection_node.py:229`起的OnnxSsdDetector，实际通过`cv2.dnn.readNetFromONNX`加载模型，并能发布同类ROS检测消息。它可作为迁移试验起点，不需要先将所有检测逻辑从零实现。

仍需确认OpenCV版本是否支持实际图、Python3与ROS/cv_bridge是否匹配，以及CPU推理与SLAM/规划同时运行的延迟和资源占用。脚本存在不等于此板可实时识别；本轮没有推理实测。CPU性能不足时才据实测决定优化或转NPU，不能先断言必然不足。

### 3.2 NPU路径

RK3399Pro使用旧系列RKNN-Toolkit及对应运行时。官方仓库明确区分它与Toolkit2，且二者不兼容，不能照搬面向其他Rockchip型号的Toolkit2教程。

工作包含：选定工具链和驱动组合；导入当前ONNX并检查算子、形状和布局支持；若使用量化则准备代表性校准数据并验证精度；实现图像预处理、推理调用、输出后处理和ROS发布；用同一批图片与原模型输出对照。

当前模型约定为RGB归一化输入，scores/boxes输出、背景加四类、归一化框坐标。转换或后端实现时若弄错通道、尺度、输出顺序、类别编号或NMS，就可能出现“程序运行但框/类别/置信度不对”。不必预设需要重新训练，也不能保证直接转换成功；若遇到不支持算子才进一步修改图或更换模型导出方式。

## 4. 通用模块能保留，但外设配置需重新对应

| 模块 | 可保留部分 | 需要重新确认 |
|---|---|---|
| Cartographer | 在线二维SLAM算法及ROS配置主体 | 依赖构建、扫描/IMU时间戳、TF及运行延迟 |
| EGO二维规划 | 地图处理、搜索/优化、轨迹与ROS接口 | 构建依赖、规划频率、规划失败和返航问题 |
| MAVROS/PX4通信 | MAVLink协议、ROS话题、设定值封装 | USB/串口设备、权限、版本与坐标转换、频率 |
| RPLIDAR | 通用Linux串口SDK及ROS驱动 | 实际设备命名、稳定别名、波特率和丢包 |
| TFmini高度 | 传感器协议及LinuxI²C调用 | 对应引脚、电平、总线启用和编号 |
| PWM舵机板 | 通过I²C控制外部PWM芯片的逻辑 | 总线、电平、引脚、供电及机构动作 |
| USB相机 | V4L2/usb_cam与图像话题主体 | 枚举编号、格式/分辨率、带宽与解码负载 |
| 任务状态机 | 航点、消息、投放及返航逻辑 | 现场新版本、禁用视觉后的流程、异常退出 |

当前location.launch用TFmini I²C bus0/address0x10、雷达/dev/ttyUSB0和MAVROS /dev/ttyACM0；UART备用路径为Nano的/dev/ttyTHS0。舵机节点默认/dev/i2c-1/address0x40。这些编号和名称并非跨板标准，需要映射至新板实际接口。

两板即使都有40针排针也不能整束照插。TB-RK3399ProD官方扩展定义包含12V、5V、3.3V及复用信号，必须按各自手册核对电源、地、逻辑电平和信号。外接PWM板承担PWM生成，通常能保留其协议；不能把原方案误写成需要重做SoC硬件PWM。

## 5. 算力与实时性需要按任务测量

标称NPU TOPS不直接代表Cartographer、EGO或ROS任务执行速度；NPU要通过适配后的推理调用才能参与检测，不会自动接管SLAM、A*、轨迹优化或串口处理。6GB为CPU/NPU分立内存的组合口径，不代表Linux可通用使用6GB，以实物内存输出确认。

需要在完整负载下检查：定位更新及消息年龄、规划耗时、控制发布间隔、视觉推理和相机端到端延迟、CPU/内存/温度及降频。问题常发生在多个节点同时繁忙时，单节点演示不能代表组合任务通过。不预判新板一定快或一定慢。

## 6. 物理集成与旧故障是两个独立问题

官方规格为12V/2A、145×106mm。供电接口、极性、调压方案、安装孔位、质量和散热均需重新核对；整机飞行影响还取决于实际重量及安装位置，尚无测量。

原板EEPROM损坏可能是故障源，也可能是供电异常的受害者；接入新板前仍需排除原机供电/外设问题。原来的SSD停滞/撞墙、终点返航失败也没有确诊为Nano硬件原因。换平台不构成这些问题已解决的证据。

## 7. 三种迁移范围及完成判据

| 目标 | 工程范围 | 主要不确定项 |
|---|---|---|
| 暂不识别，恢复导航任务 | 建立系统与ROS环境、构建通用节点、映射外设、调整实际任务流程 | 现场代码、驱动与构建、SLAM/规划实时性、返航故障 |
| 恢复CPU识别 | 以上加OpenCV ONNX后端和任务联动 | 模型/库兼容、识别精度、CPU余量与端到端延迟 |
| 恢复NPU识别 | 以上加RKNN模型转换、运行时和ROS后端 | 算子/版本支持、校准与精度、输出等价、组合负载 |

上述是相对工作范围，不是完成时长承诺。若采购前能借板验证，应先确认固件与恢复资料，再做通用模块构建和离线数据回放；需要识别时先做当前模型转换/CPU推理试验。确认关键接口及性能后再决定是否将其作为主机平台。

`ssd_detection/CMakeLists.txt:107–110`缺依赖时会跳过Jetson C++目标，所以catkin退出0只证明已选目标构建成功。应列出实际生成的目标和排除项；不识别阶段可以有意排除视觉，但须明确验收范围。恢复任务还需证明传感器、规划、设定值及异常退出工作，而不能仅以“板能开机”“ROS话题有数据”为完成。

## 8. 与SHELL补充的原机组合对比

SHELL进一步明确原机为 **NVIDIA Jetson Nano 4GB P3448-0020 SOM＋JETSON-IO-BASE-A Rev2 carrier board**。该具体硬件标识来源为SHELL补充，助手未重新核验实物标签。NVIDIA早期官方适配指南使用P3448-0020并注明完整料号900-13448-0020-000，后续文档也可见P3448-0002命名；采购和刷写须按实物标签、完整料号及配套资料确认。

| 项目 | 原Nano 4GB＋BASE-A Rev2 | TB-RK3399ProD标称6+32GB |
|---|---|---|
| 形态 | Jetson可拆SOM＋载板，模组为260针边缘接口 | 完整Rockchip开发板，不是兼容Nano插槽的替换SOM |
| CPU | 四核Cortex-A57，最高约1.43GHz | 双核Cortex-A72＋四核Cortex-A53，最高1.8GHz |
| GPU | 128 CUDA核心Maxwell | Mali-T860 MP4，不执行CUDA/TensorRT后端 |
| 独立NPU | 无；现有识别依靠GPU | 有，官方标称最高3TOPS；需RKNN适配 |
| 内存 | 4GB LPDDR4，64bit、25.6GB/s，CPU/GPU共享物理内存 | LPDDR3，6GB配置含CPU侧4GB及NPU侧2GB，不是Linux通用6GB；实物需核实 |
| 板载存储 | 生产模组16GB eMMC；原机历史核验根目录实际在SD | 截图标称32GB eMMC，另有TF槽 |
| USB-A | 载板4个USB3.0口 | 1个USB3.0 Host＋2个USB2.0 Host，另有Type-C USB3.0 OTG |
| 有线网络 | 千兆以太网 | 千兆以太网 |
| 无线 | M.2 Key E或USB扩展；原机无线型号另核 | 官方板载2.4GHz Wi-Fi和BT4.2 |
| 显示 | 载板HDMI及DP | HDMI、DP，另有MIPI/eDP扩展 |
| 扩展 | GPIO/I²C/SPI/UART等，排针按BASE-A定义 | GPIO/I²C/SPI/ADC/I²S等，40针定义不同且含12V电源 |
| 外部电源 | BASE-A系列DC口5V，厂商配套5V/4A | 官方DC 12V/2A |
| 占地 | 厂商BASE-A套件系列约100×80mm，Rev2以实物尺寸确认 | PCB 145×106mm，机架安装需重新核对 |
| 当前工程适配 | Jetson专用识别后端与原有部署环境相匹配 | 通用模块可移植，视觉和板级驱动需适配 |

额定适配器5V×4A与12V×2A不是实际功耗，不能直接据此比较续航。核数和频率也不是整套任务性能结论；RK的CPU架构/核数具有通用计算潜力，但新板SLAM、规划及完整负载须实测。3TOPS NPU数值不能直接与Nano GPU的不同精度算力换算成任务速度倍数。

Nano 4GB是CPU/GPU共享内存，不表示GPU和CPU各自拥有4GB；RK分立NPU内存也不能随意给ROS/SLAM使用。TB更大的eMMC不等于解决原机容量问题，原机历史上已把根目录放在SD，完整启动链仍须另外核对。

对项目而言：MAVROS/规划/定位逻辑通常能保留；CUDA识别实现不能直接保留；供电、排针和系统镜像不能互换；新板健康状态、实测性能以及旧识别/返航故障仍分别验收。

## 9. SHELL澄清：只比较性能

SHELL明确需要听性能差异。此前关于CPU“有潜力”的架构判断不能充当实测性能提升结论，本节补充量化参考并与兼容性分开。

### CPU参考：同档次，部分多线程负载RK侧小幅领先

[sbc-bench原始结果汇总](https://github.com/ThomasKaiser/sbc-bench/blob/master/Results.md)给出Jetson Nano在约1480MHz时7-Zip单线程1578、多线程5260；采用相同CPU核心组合的RK3399 RockPro64在1800/1400MHz的两条arm64记录分别为单线程1580/1673、多线程6140/6420。对应单线程接近或约高6%，多线程约高17%/22%。

这是不同板、内存和系统下的一项整数压缩基准，既不是TB-RK3399ProD实测，也不是浮点SLAM/规划测试；只能支持“同档次，部分CPU多线程负载可能小幅提升”，不能承诺该板全任务快20%或六核必胜四核。未使用Nano 2GHz及RK超频条目作常规性能比较。

### AI理论峰值：必须区分数据精度

[NVIDIA官方说明](https://forums.developer.nvidia.com/t/help-question/71758)给出Nano GPU峰值472GFLOPS FP16、236GFLOPS FP32。[Rockchip官方数据手册](https://opensource.rock-chips.com/images/9/9f/Rockchip_RK3399Pro_Datasheet_V1.1_20181214.pdf)列出NPU每周期1920次INT8 MAC、64次FP16 MAC；产品标称INT8峰值约3TOPS，不能当作FP16。

按相同频率和相同MAC计数口径换算，FP16峰值约为3×64/1920＝0.1TFLOPS，即约100GFLOPS。这是由官方规格推算的理论值，不是板上实测；Nano约472GFLOPS对应约4.7倍于该NPU的FP16峰值，不包括Mali GPU，更不代表完整识别程序帧率有4.7倍差距。RK优势主要在适合其NPU且完成量化的INT8推理，是否胜出取决于具体模型、算子、访存和数据搬运。

### 实际推理例子与适用边界

[DeepEdgeBench（2021）](https://arxiv.org/html/2108.09457)对Jetson Nano与采用RK3399Pro的ASUS Tinker Edge R测试5000张图的MobileNetV2分类推理。非量化模型的Nano TensorRT结果为118.737秒/5000张≈23.75毫秒/张，RKNN结果760.7秒/5000张≈152.14毫秒/张；该条件下Nano约快6.4倍。

此例不等于TB板性能：RK侧是另一块板、内存配置不同；工具链为当年的版本；模型为MobileNetV2分类，不是本项目MobileNetV1骨干SSD检测；计时不含图片预处理与结果评估。该例只说明同芯片NPU并不因3TOPS就保证更快，不能作为当前SSD帧率预测。未拿文中TensorFlow对比当作纯CPU性能结论。

对当前项目的性能判断：取消识别后，主要比较CPU、内存和组合任务延迟，两者仍属同档次，RK不构成已证实的大幅升级；保留原浮点推理时Nano的峰值与已有对比更有利；适配INT8 NPU后RK存在性能优势可能，但须当前模型实测。原机停滞/返航失败尚无CPU饱和等性能证据，不能归因为算力不足。
