### 22.3. 第一阶段：补主机密钥，随后按真实EXEC错误调整方向

离线检查FULL-v2镜像时，`/etc/ssh`只有`moduli`、`ssh_config`和`sshd_config`，没有默认`ssh_host_*`主机密钥；SSH主服务单元还设置了启动前执行`/usr/sbin/sshd -t`。因此最初给出的修复是：

```bash
sudo ssh-keygen -A
sudo systemctl reset-failed ssh
sudo systemctl restart ssh
sudo ss -ltnp 'sport = :22'
```

`ssh-keygen -A`用于生成缺失的服务器主机密钥，已有默认密钥不覆盖。它建立服务器身份，不是修改jcfh的登录密码。`reset-failed`清理服务失败记录及启动限速状态；`restart`尝试重新启动；`ss`用于查看22端口是否监听。此处是当时的方案记录，不应在当前已登录成功时重新照做。

随后SHELL反馈启动仍失败，并提供23:26:12–13的实际日志，核心是：

```text
Failed at step EXEC spawning /usr/sbin/sshd: No such file or directory
Control process exited, code=exited status=203
Start request repeated too quickly
```

这说明当时systemd连目标程序都没能成功执行；仅补密钥不能解决这一层错误。最后一行是连续启动失败触发限速后的结果，需要先解决前面的执行错误。原镜像中`/usr/sbin/sshd`、其AArch64 ELF格式及`/lib/ld-linux-aarch64.so.1`加载器均存在，所以没有证据把它写成“原镜像必然缺少sshd”。现场文件或执行环境与原镜像之间的具体差异未取得。

当时改为提供`sudo apt update`、`sudo apt install --reinstall -y openssh-server`恢复软件包文件，再刷新并重启服务的方案。SHELL后续照片显示重装进入安装后配置，但该配置仍失败，不能记作重装全程成功。证据见[实际EXEC失败日志](../docs/验证记录/RK_SSH核查_2026-10-23/板端SSH_EXEC失败日志_SHELL提供.txt)、[主机密钥与主服务单元核查](../docs/验证记录/RK_SSH核查_2026-10-23/镜像SSH服务与主机密钥元数据.json)和[sshd可执行文件核查](../docs/验证记录/RK_SSH核查_2026-10-23/镜像sshd可执行文件核查.json)。

### 22.4. 第二阶段：手动检查不报错，服务却在另一个程序上失败

SHELL提供的IMG_1634.jpeg显示：

- `openssh-server`安装后脚本返回1，dpkg配置尚未完成。
- 手动执行`sudo install -d -m 0755 /run/sshd`，再执行`sudo /usr/sbin/sshd -t`，没有显示错误文本；照片没有单独展示退出码。
- SSH服务日志的失败目标已变为`/usr/sbin/ssh-keygen`，仍是203/EXEC。

`/run/sshd`是运行时目录，手动测试前创建它可以避免停用服务时目录已被systemd清理所带来的干扰；主服务本来就配置了`RuntimeDirectory=sshd`。`sshd -t`只检查sshd配置与密钥等条件，不会替systemd执行SSH服务的全部启动前命令。因此“手动检查没有错误”与“整个服务仍然启动失败”可以同时成立。

这次必须查看主服务之外的补充配置。离线读取原镜像，找到：

```text
/etc/systemd/system/ssh.service.d/10-hostkeys.conf
```

其内容为：

```ini
[Service]
# Host keys are removed from the image; regenerate them on the first boot.
ExecStartPre=/usr/sbin/ssh-keygen -A
```

该文件的用途是让服务在启动前补建主机密钥，但程序路径写错。实际核查结果为：

| 路径／归属                                         | 原镜像核查结果       | 对本次故障的意义                             |
| -------------------------------------------------- | -------------------- | -------------------------------------------- |
| `/usr/bin/ssh-keygen`                              | 程序存在且路径可解析 | 应调用的正确位置                             |
| `/usr/sbin/ssh-keygen`                             | 不存在               | 与现场EXEC错误路径一致                       |
| `10-hostkeys.conf`是否列在openssh-server包文件清单 | 未列出               | 不能指望重装openssh-server自动改正该补充文件 |

systemd将主服务单元与`.service.d/*.conf`一起加载。服务执行到这一条`ExecStartPre`时，因绝对路径不存在而失败，主SSH守护进程无法按这次启动流程运行。即使终端中直接输入`ssh-keygen`能通过PATH找到正确程序，也不能修正服务里已经写死的错误绝对路径。

前次只读核查覆盖了主单元，漏查补充配置，这是定位绕行的原因。本轮依据新的现场错误补查drop-in，才找到最后的具体阻塞点。完整证据见[SSH补充配置密钥程序路径核查](../docs/验证记录/RK_SSH核查_2026-10-23/SSH补充配置密钥程序路径核查.json)。

**路径来源补充（SHELL查阅反馈）：** SHELL报告在`t.rock-chips.com`的TB-RK3399ProD相关主分支`overlay/etc/...`资料中找到了固定sbin路径的来源，认为该配置沿用到Ubuntu后造成此次SSH启动问题。这与本次镜像中补充配置固定调用`/usr/sbin/ssh-keygen`、而实际程序位于`/usr/bin/ssh-keygen`的证据一致。具体上游页面、仓库及提交版本未留存核对，本条按SHELL提供的来源线索记录；按SHELL要求不再继续追溯。

### 22.5. 最终交付的修复命令及每一步的作用

以下为本次最终提供给SHELL的板端操作顺序，保留用于同类故障复现时回查；当前SSH已能登录，无需重复执行：

```bash
sudo sed -i.bak 's|/usr/sbin/ssh-keygen|/usr/bin/ssh-keygen|g' /etc/systemd/system/ssh.service.d/10-hostkeys.conf
sudo systemctl daemon-reload
sudo systemctl reset-failed ssh
sudo systemctl restart ssh
sudo dpkg --configure -a
sudo ss -ltnp 'sport = :22'
```

| 顺序 | 操作与作用                                                                                  | 结果应如何判断                                                                         |
| ---- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1    | `sed -i.bak`把补充文件中的错误绝对路径替换为正确路径，并保留`10-hostkeys.conf.bak`备份      | 实质修复点是路径改正；备份后缀不是`.conf`，不作为同目录的补充单元加载                  |
| 2    | `daemon-reload`让systemd重新读取主单元和补充配置                                            | 更新管理器加载的服务定义；这一步本身不会启动sshd                                       |
| 3    | `reset-failed ssh`清理ssh的失败状态及连续失败触发的启动限速                                 | 为修正后重新启动清除限速障碍；它本身也不启动服务                                       |
| 4    | `restart ssh`按新加载的定义重新启动SSH服务                                                  | 启动前命令及主进程均须成功，不能只看命令已输入                                         |
| 5    | `dpkg --configure -a`继续配置全部已解包但尚未配置的软件包，其中包括此前失败的openssh-server | 用于补完软件包配置收尾；范围不只SSH，最终是否全部成功须看实际输出                      |
| 6    | `ss -ltnp 'sport = :22'`查看本地TCP22的监听与进程信息                                       | 预期出现`LISTEN`和sshd；本次没有另行取得这条输出的归档，以后续真实登录作为服务可用证据 |

`sudo`表示用管理员权限执行这些系统配置操作。此处`daemon-reload`与之前Wi-Fi修复中的作用相同：让systemd读入磁盘上的新定义；具体哪个服务恢复，由后续`restart ssh`决定。最终修正没有更换Wi-Fi管理器、重刷系统或修改登录账户。
