### 早期提出的联网方案与选择理由

此前讨论过路由器、无线网络和网线直连；根据“轻薄本无网口、Nano 无显示器”的条件，今日优先选择**尝试 Micro-USB 虚拟网卡直连**。这是助手提出的待验证方案，不能推断为学长原来使用的方法。

| 方案 | 条件与用途 | 当前判断 |
|---|---|---|
| **Micro-USB 数据线直连** | Nano 系统启用 USB 设备网络功能，Windows 能识别网络设备；通常尝试地址 `192.168.55.1` | **优先验证**，无需路由器或轻薄本网口 |
| Nano 网线接路由器 LAN，电脑接同一路由器 Wi-Fi | 可用路由器和网线；Nano 获得地址，网络允许设备互访；可从路由器客户端列表找 IP | 可作为备选，不要求 Nano 接显示器 |
| Nano 与电脑连接同一 Wi-Fi／热点 | Nano 已有可用无线网卡，且已配置该无线网络，或已有途径为其配置 | 无线硬件与配置未核实，不能默认可行 |
| 轻薄本 USB 转网口后用网线直连 Nano | 需要转接器，并处理两端 IP 配置 | 备选，不默认插线即可通信 |

**USB 方案依据：** [Waveshare 载板产品说明](https://www.waveshare.com/jetson-nano-dev-kit-a.htm?sku=21650)明确 Micro-USB 可用于数据传输；[Waveshare JetBot AI Kit 的 Remote Operation 说明](https://www.waveshare.com/wiki/JetBot_AI_Kit#Remote_Operation)提供 Nano 正常启动后经 Micro-USB、SSH 连接 `192.168.55.1` 的方法。后者是该功能的参考依据，**尚不能证明本机 Rev2 载板搭配团队现有镜像已启用该服务**；也不沿用 JetBot 镜像的默认账号密码。

### 早期拟定的操作与验收点

1. 保留 Nano 已确认正确的独立供电，使系统正常启动。使用**支持数据传输的 Micro-USB 线**连接电脑 USB 口和 Nano 载板的 Micro-USB 口；不使用双头 USB-A 线，不依靠电脑 USB 给整套设备供电，不进入 Recovery 刷机模式。
2. 等待系统启动，检查 Windows 是否新增 USB/RNDIS 网络设备。
3. 在 **Windows PowerShell** 测试候选地址的 SSH 端口：

   ```powershell
   Test-NetConnection 192.168.55.1 -Port 22
   ```

   `TcpTestSucceeded : True` 表示目标地址的 TCP 22 端口可达，还不代表账户认证成功。

4. 确认端口可达后，尝试截图中出现的账户：

   ```powershell
   ssh jcfh@192.168.55.1
   ```

   使用现有 Nano 账户密码，不在日志中记录密码。若账户已变更，使用实际用户名。成功进入远程 shell 才记为“SSH 登录完成”。

5. 登录后先检查 ROS 环境、脚本是否存在及其内容，核对舵机型号、电压、控制引脚和供电接线；确认脚本启动时是否会自动动作、角度范围是否合适，再按学长流程测试。推进电机保持停转，舵机首次动作避免直接尝试大角度。
6. 若没有 USB 网络设备，先检查数据线、接口、设备识别和驱动；若已有网卡但端口不通，再检查 IP、系统启动、USB 网络服务及 SSH。若出现可用 USB 串口，可进一步评估串口登录入口。

**早期阶段结论：** 当时仅整理学长流程、核实电脑 SSH 客户端并提出 USB 方案；USB、登录、脚本及舵机动作当时尚未验收。后续进展如下。

## 连接过程复盘

### 1. 第一次 Micro-USB 检查：还没有设备识别证据

`[助手实测]` 检查 Windows 网卡、IPv4 与当前 USB/PnP 设备，没有发现 Nano 对应网卡、串口或 NVIDIA USB 设备。重插后再次检查，仍没有新增 Nano 设备。`192.168.55.1:22` 探测超时；当时测试走电脑 WLAN 和校园网网关，而不是 USB 接口。

**当时优先查 USB 枚举的原因：** SSH 必须先有可用网络接口和通路。目标 USB 网卡根本没有出现时，修改 SSH 密码、角度或 ROS 程序不能补上这一层。助手还检查了 PnP 历史和设备安装日志，未找到 Nano 的枚举或相关驱动安装失败证据，没有据此安装陌生驱动。

**结论边界：** 早期未识别的具体原因没有查明。不能认定线只支持充电、板卡不支持 USB 网络或 Nano 损坏；后来的成功枚举证明最终所用连接能传输 USB 数据。电源灯亮只是一条现场线索，不能代替网卡、IP、端口和账户登录的验收。

### 2. 转向 iPhone 热点：先明确第一次配置入口

`[SHELL报告]` 起初没有配置过 Nano 热点，或不确定。随后确认 Nano 有无线网卡。曾计划让 **Nano 和电脑都连接同一个 iPhone 热点**，再使用 Nano 在该热点下获得的地址进行 SSH。

**方案卡点：** 把电脑连到热点，不会自动把热点名称和密码配置进 Nano。首次配置需要 Nano 本地桌面／终端，或另一条已经可登录的连接。仅有无线硬件也不等于驱动、配置和设备互访已正常。因此当时继续寻找首次配置入口，没有虚构一个热点 IP。

iPhone 设置方法是“设置 → 个人热点 → 允许其他人加入”；搜不到时可尝试“最大兼容性”（机型提供该选项时）。热点名称跟随 iPhone 设备名称。[Apple 官方说明](https://support.apple.com/zh-cn/111785)

**本次结果：** 完成条件确认和操作指导，未保存 Nano 加入 iPhone 热点、热点 IPv4 和该链路 SSH 成功的证据。

### 3. 发现已有路由器：电脑无网口仍可建立局域网

`[SHELL报告]` 有 TP-Link 路由器和网线，管理入口为 `tplogin.cn`；没有提供具体型号。可行拓扑为：

```text
Nano 网口 ──网线── 路由器 LAN 口
电脑     ──Wi-Fi── 同一个路由器的主人网络
```

电脑通过 Wi-Fi 进入路由器局域网即可，不要求电脑有网口，也不依赖 Nano 的无线网卡。Nano 地址应从路由器连接设备／DHCP 列表或 Nano 本地接口信息读取。访客 Wi-Fi 可能隔离局域网设备，调试优先用主人网络。[TP-Link 连接说明](https://service.tp-link.com.cn/detail_article_2041.html)、[访客网络说明](https://service.tp-link.com.cn/detail_article_2896.html)

**局域网访问和互联网访问是两件事：** Nano 与电脑同处可互通 LAN 时，SSH 本身不要求路由器有外网；但电脑离开当前校园网、转入没有外网的路由器后，在线聊天和远程协助可能中断。如果希望路由器从 iPhone 热点取得外网，需要核实该具体型号是否支持无线中继／WISP；仅知道 TP-Link 品牌或 `tplogin.cn` 不能确定功能。

**本次结果：** 作为备选方案完成分析，没有完整连通验收。后面出现 `192.168.1.x` 地址，不足以替代这条路径的端口和登录验证。

### 4. 用电视获得本地操作入口

`[SHELL报告]` 现场找到电视；计划并完成 Nano HDMI 接电视，电视先显示 NVIDIA 标识，随后进入 Ubuntu 桌面。HDMI 是显示通道；USB 键盘接 Nano，配合本地操作。普通笔记本 HDMI 口通常是输出，不能默认把笔记本屏幕用作 Nano 的 HDMI 显示器。[NVIDIA 显示器与键鼠操作说明](https://developer.nvidia.com/embedded/learn/get-started-jetson-nano-devkit)

Ubuntu 的 Terminal 图标能够找到，但点击时没有窗口或立即关闭。助手提供了应用搜索、`Alt+F2` 运行 `gnome-terminal`、从图形网络菜单配置热点等替代入口。后来SHELL报告终端可以打开。**没有取得该启动失败的报错，也没有证明是哪种方法修复了它；不把它归因为 Python、区域设置或系统损坏。** 今天没有为此升级、重装或改系统 Python。

电视方案随后用于检查 Nano 本地状态：`hostname -I` 输出多个地址；`systemctl is-active ssh` 返回 `active`。这确认了 SSH 服务在运行，具体监听端口与实际链路还要从网络侧验证。

### 5. Micro-USB 后来成功枚举，出现网卡和串口

SHELL发现指示灯常亮后要求再试原方案。`[助手实测]` 这次 Windows 出现：

| 设备 | 本次名称／索引 | 用途与状态 |
|---|---|---|
| NVIDIA USB 复合设备 | `VID_0955 / PID_7020` | 当时正常系统的 USB 设备模式已被识别 |
| RNDIS 网卡 | `以太网 3`，`ifIndex 42`，`Remote NDIS Compatible Device` | Up；本次最终使用它进行 SSH |
| NCM 网卡 | `以太网 2`，`ifIndex 38`，`UsbNcm Host Device` | Up；未给它同时配置同网段固定地址 |
| USB 串口 | `COM5` | 可提供本地串口登录入口 |
| 只读说明卷 | 当时为 `E:`，卷标 `L4T-README` | 提供该镜像自带 USB 说明 |

助手以 `115200、8N1` 短暂打开 COM5，仅发送回车读取提示并关闭。收到 `Ubuntu 18.04.6 LTS jcfh-desktop ttyGS0` 和 `jcfh-desktop login:`，**没有通过串口完成账户登录**。

这些接口属于运行中系统提供的 USB 网络、串口和只读卷。Recovery/APX 是另一类恢复／刷机状态，不能把它当作可直接 SSH 的网络入口。

### 6. 有网卡仍超时：DHCP 地址未取得或很快丢失

最初 RNDIS 是 `169.254.1.199/16`，NCM 是 `169.254.207.46/16`。这类自动地址没有建立本次需要的 `192.168.55.0/24` 直连通路。

`[助手实测]` 执行 `ipconfig /renew "以太网 3"` 后，RNDIS 得到 `192.168.55.100/24`，SSH 立即有认证响应。随后SHELL再次遇到 timeout；助手复查 RNDIS 仍 Up，但 IPv4 已丢失，再续租又恢复 SSH 响应。

**关键证据：** RNDIS 的 DHCP 服务器为 `192.168.55.1`。两次租约分别是 `22:12:08 → 22:12:23`、`22:12:42 → 22:12:57`，都只有 **15 秒**（本机记录，上海时间）。稍后快照又回落至自动地址，与短租约到期后续租未成功的现象一致。

**根因边界：** 尚未查明为何没有稳定续租。不能断言 CPU／磁盘负载、双 USB 网卡、IP 冲突或某条 dnsmasq 配置就是根因。日志中 DHCP 事件 1001、错误 `0x79` 对应的是 NCM，不能写成 RNDIS 的续租失败日志；最近查询未发现冲突事件，也不意味着已彻底排除所有冲突。

镜像自带说明明确推荐：发生 DHCP 响应不及时、IPv4 掉线时，电脑可固定为 `192.168.55.100`，掩码 `255.255.255.0`，无网关和 DNS；RNDIS 与 NCM 支持任选其一，避免同时配置两者。[已归档 USB 官方说明](附件/2026-10-01/README-usb-dev-mode.txt)

### 7. 固定电脑 USB IPv4：先遇到权限限制，再由SHELL完成

```powershell

```

| 参数 | 本次选择的含义 |
|---|---|
| `name="以太网 3"` | 只设置本次确认的 Nano RNDIS 网卡；下次名称可能变化 |
| `source=static` | 使用手工 IPv4，绕过本次短 DHCP 租约 |
| `address=192.168.55.100` | 电脑 USB 端地址，与 Nano `.1` 配对 |
| `mask=255.255.255.0` | `/24` 子网，双方在同一个 USB 直连网段 |
| `gateway=none` | 不让 USB 直连承担默认互联网出口；保留电脑其他网络的出口 |
| `store=active` | **仅当前 Windows 启动期间有效，下次电脑重启后需复查／重新设置** |

`[助手实测]` 复查得到 `.100/24`、`PrefixOrigin=Manual`、`AddressState=Preferred`、DHCP Disabled；间隔 20 秒后地址仍在，SSH 仍有响应。这里只验证本次观察窗口，不等同于长时间压力测试。没有同时配置 NCM，也没有改变电脑 WLAN 的网关或 DNS。[微软 netsh 参数说明](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-interface)

## 连接方案比较

**SSH 是远程登录协议；Micro-USB、Wi-Fi 热点和路由器局域网是承载它的网络方式。HDMI 是本地显示入口，不传输 SSH 网络。** 正确流程是先让设备可识别并取得可互通的地址，再测试端口，最后完成认证。

| 方式 | 必要条件 | 优点 | 局限／调试重点 | 今日结论 |
|---|---|---|---|---|
| Micro-USB 虚拟网卡＋SSH | 数据线、正常启动的 Nano、镜像 USB 设备网络、电脑驱动和 IPv4 | 不需要电脑网口、路由器或 Nano Wi-Fi；可保持电脑当前上网连接；地址易复现 | 必须等系统启动并枚举；DHCP可能不稳定；固定 IP 要管理员权限；接口名称可能变化 | **已连通并登录，本次优先复用** |
| 同一 iPhone 热点＋SSH | Nano 无线网卡和驱动；先配置热点；双方接入且能互访 | 可移动操作、减少 USB 连线；手机可提供外网 | 首次配置有入口要求；无线稳定性、手机电量、地址变化及设备互访需实测 | 方案未验收 |
| Nano 网线接路由器 LAN，电脑接路由器 Wi-Fi | 路由器、网线、主人 Wi-Fi、DHCP／合适静态地址 | 电脑无网口也可用；Nano无需Wi-Fi；适合固定台架或多人局域网调试 | Nano IP需查询；访客隔离；无WAN时仅局域网；中继iPhone需型号支持 | 方案未完整验收 |
| HDMI 电视＋USB键盘，本地桌面／终端 | HDMI线、合适显示输入、键盘；鼠标更方便 | 可直观看开机、配置首次网络、诊断SSH不可达；不依赖远程网络 | 需要现场屏幕和键鼠；显示成功不代表网络成功 | SHELL报告已进入桌面并可开终端 |
| USB 串口登录 | USB已枚举COM口、串口终端、账户 | 无需USB IPv4，网络故障时可作备用本地入口 | 仍依赖USB设备识别；需正确端口和参数；只有文字界面 | 助手只验证登录提示，未登录 |
| USB转网口后网线直连电脑与Nano | 额外转接器和双方IP配置 | 不依赖Nano Wi-Fi，可使用有线链路 | 今日工具清单没有转接器；直插网线不保证自动同网段 | 仅备选建议 |

## Micro-USB 重复连接手册

### A. 接线、启动与识别

Nano 按已确认的电源方案启动，数据线连接电脑与载板 Micro-USB；需要本地观察时保留电视。等待系统正常启动。**本流程不进入 Recovery，也不刷机。**

在 **电脑 Windows PowerShell** 运行：

```powershell
Get-NetAdapter | Format-Table ifIndex,Name,InterfaceDescription,Status
Get-NetIPAddress -AddressFamily IPv4 | Format-Table InterfaceAlias,IPAddress,PrefixLength,AddressState
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match 'VID_0955' } | Format-Table Status,Class,FriendlyName
```

先找 `Remote NDIS Compatible Device`。本次名称是“以太网 3”，不是永久名称；`ifIndex 42` 和 `COM5` 也只对应本次枚举。没有识别时按供电、启动、数据线、接口和PnP错误定位；不要把灯亮当作网卡已识别。

### B. 检查IPv4，必要时恢复本次固定配置

如果电脑已有 `.100/24`、Nano USB为 `.1`，直接进入端口测试。若电脑为 `169.254.x.x` 或没有IPv4，可以对**已确认的USB网卡**续租：

```powershell
ipconfig /renew "以太网 3"
```

如果再次出现短租约或掉地址，使用**管理员 PowerShell**执行今天验证过的静态命令；先把网卡名称替换为当前实际名称：

```powershell
netsh interface ipv4 set address name="以太网 3" source=static address=192.168.55.100 mask=255.255.255.0 gateway=none store=active
```

Nano 镜像默认 `.1` 来自其自带说明，不是任意USB设备通用地址；重刷镜像或改变网络配置后应重新核实。`store=active` 会在电脑重启后失效，本次没有改成永久静态配置。记录本次修改只作用于USB接口。

如以后需要主动恢复该USB接口的DHCP，在管理员PowerShell使用：

```powershell
netsh interface ipv4 set address name="以太网 3" source=dhcp store=active
```

这是一条回退方法，今天未执行；恢复后仍需确认该镜像的短租约问题是否重现。

### C. 验证端口和路由，再登录

在 **电脑 Windows PowerShell**：

```powershell
Test-NetConnection 192.168.55.1 -Port 22 -InformationLevel Detailed
```

重点看 `TcpTestSucceeded`、`InterfaceAlias`、`SourceAddress`：本次USB链路应从实际USB网卡、源地址 `.100` 访问 `.1`。如果仍走WLAN，先检查USB地址和路由。Ping失败并不单独等于SSH失败，TCP 22结果更直接。[微软诊断说明](https://learn.microsoft.com/powershell/module/nettcpip/test-netconnection)

然后登录：

```powershell
ssh -o ConnectTimeout=10 jcfh@192.168.55.1
```

密码使用现有Nano账户密码，输入时不显示。看到 `jcfh@jcfh-desktop:~$` 才进入Nano远程shell；此后的Linux命令在这个窗口执行。首次主机公钥提示应核对连接的设备；若以后提示主机身份改变，先确认IP是否指向原Nano、是否重刷，不通过关闭主机密钥检查来掩盖问题。

### D. 备用入口

USB网络不通但能看到COM口时，可用串口终端选择实际COM口、`115200、8N1`（8数据位、无校验、1停止位）、无流控；本次助手已经读到COM5的登录提示。若有电视，优先通过Nano本地终端查询状态。只读说明卷原文的8N1解释有笔误，归档保留原文，本手册采用正确含义。

### E. 电视本地操作与终端入口

1. Nano的HDMI口接电视HDMI输入，遥控器选择实际插入的HDMI编号；USB键盘接Nano的USB-A口，鼠标有的话一并接上。
2. Nano按正确电源方案启动。看到NVIDIA标识说明已有视频信号，仍需等Ubuntu登录页或桌面；登录现有账户。
3. 用接在Nano上的键盘按 `Ctrl+Alt+T`。若快捷键无反应，可按Windows标志键搜索 `Terminal` 并回车，或 `Alt+F2` 输入 `gnome-terminal` 回车。[Ubuntu应用启动说明](https://help.ubuntu.com/stable/ubuntu-help/shell-apps-open.html.en)
4. 若Terminal图标启动即关闭，先保留报错和出现条件；可从桌面网络菜单配置连接、在设置详情查看IP，或用已可用的USB串口／SSH入口继续诊断。今天终端后来打开的原因没有确定，这些入口不能被记成已验证修复方案。
5. 本地终端和SSH终端都运行Nano上的Linux命令；电脑本地PowerShell运行Windows命令。先根据提示符判断所在机器，再输入命令。

## 分层排障

| 现象 | 首先检查 | 今天的对应经验 |
|---|---|---|
| 没有USB网卡/串口/NVIDIA设备 | Nano启动、供电、数据线、接口、PnP错误 | 早期处于此层；根因没有确定 |
| USB网卡Up，但`169.254.x.x`或无IPv4 | DHCP、手工地址、网段、接口选择 | 后期卡在此层，固定USB IPv4后改善 |
| `.100`出现后又消失 | 租约时间、续租、接口重建 | 今日查到15秒租约；不直接推断服务内部根因 |
| `Connection timed out` | 设备、IP、路由、链路、目标端监听/防火墙 | 今天先是无USB，后来是USB IPv4丢失，不能只归结为密码 |
| `Connection refused` | 目标端口监听、服务状态，及拒绝策略 | 今日未出现；需要Nano本地状态作进一步判断 |
| 出现`password:` | 已进入认证阶段，使用正确账户 | 说明该次SSH连接已推进到认证 |
| `Permission denied` | 用户名、密码、公钥或认证策略 | 助手未提供凭据时与SHELL密码首次失败要分别记录 |
| 主机公钥改变警告 | 核实设备身份、IP变化、镜像是否重刷 | 今日没有该警告；不要直接关闭检查 |
| SSH登录成功，但ROS/Python报错 | 环境、依赖、硬件接口、程序自身 | 已经是另一层问题，不继续改USB地址来修复代码 |

在 **Nano本地/SSH终端** 可用的只读定位命令：

```bash
hostname -I
ip -4 addr show
ip -4 route
systemctl is-active ssh
systemctl status ssh --no-pager
ss -ltn
```

`active`表示服务运行，`ss -ltn`再看22端口监听。服务未运行时，先阅读 `systemctl status` 的完整输出；确认是该服务问题后再考虑启动服务。串口、本地桌面和网络入口用于相互交叉验证。仅当实际问题涉及防火墙时才检查对应规则，不统一关闭防火墙。

## 舵机程序与测试流程

源码来源为SHELL在Nano上读取后提供的内容，归档为[SHELL提供的舵机源码快照](附件/2026-10-01/servo_controller_用户提供快照.py)。它是本次源码快照，不是助手修改后部署的程序，也没有与Nano原文件做哈希比对。实际运行路径仍为：


### 控制链路与通道

脚本使用ROS 1 `rospy`，通过 `ServoKit(channels=16)` 控制PCA9685兼容舵机驱动。`kit.servo[0]`、`[1]`是驱动板通道0和1。`LED_Pin='SPI1_MOSI'`对应LED相关GPIO，注释标为物理19号针；它不能被记录为两路舵机的PWM输出脚。[ServoKit用法](https://learn.adafruit.com/16-channel-pwm-servo-driver/python-circuitpython)

`[源码确认]` 程序初始化后**自动下发0号170°、1号30°，不等待用户输入**；正常离开 `rospy.spin()` 后又下发0号170°。实际板卡型号、舵机规格和PWM标定仍需独立记录。

| 人工输入 | 源码动作 |
|---|---|
| `aN` | 通道0设为N度，代码接受整数0～180 |
| `bN` | 通道1设为N度，代码接受整数0～180 |
| `f` / `F` | 通道0设为170°（初始角度变量） |
| `d` / `D` | 通道0设为55°（识别角度变量） |
| `o` / `O` | 通道1设为120° |
| `c` / `C` | 通道1设为30° |
| `l` / `L` | LED闪烁3次，每次高、低电平各1秒 |

脚本另订阅 `/gpio_cmd`（`std_msgs/String`）：

| 消息内容 | 源码动作 | 今日验收范围 |
|---|---|---|
| `Front`、`Down` | 通道0设170°、55° | 未逐消息验收 |
| `Drop` | 通道1设120°，4秒后设30° | 未验收自动投放流程 |
| `PUT1` | 通道0设150°，2秒后设10° | 未逐消息验收 |
| `PUT2` | 通道1设130°，2秒后设12° | 未逐消息验收 |
| `PUT3` | 通道2设45°，2秒后设175° | 第三通道未验收 |
| `Blink` | LED高1秒后低 | LED实际动作未报告 |

若 `ModuleNotFoundError`，核对这个 `python3` 的版本、路径及已安装依赖；今天已正常动作，先保留现状。升级系统Python、替换系统解释器链接、安装最新版ROS或Adafruit库都不作为通用第一步。

### 2. I²C能访问、PWM能输出、舵机能动作分开诊断

```bash
ls -l /dev/i2c-*
groups
```

若已有 `i2cdetect`，可用 `i2cdetect -l`列出总线；进一步扫描只针对已确认的舵机驱动总线，不随意扫描所有总线或强制写寄存器。`PermissionError`先查设备权限；`No I2C device at address`／`Remote I/O error`再查总线、地址、逻辑供电、SDA/SCL、共地和连接稳定性。

官方ServoKit接口默认参数包含地址 `0x40`、PWM频率50Hz，实际以Nano安装版本及驱动板地址配置为准，今天没有测量PWM波形。驱动板VCC逻辑电源与V+舵机电源职责不同：I²C能访问不保证舵机电源有效。供电电压和电流容量按实际舵机/驱动板规格核定，不仅凭库默认值判断。[ServoKit API](https://docs.circuitpython.org/projects/servokit/en/latest/api.html)、[驱动板引脚说明](https://learn.adafruit.com/16-channel-pwm-servo-driver/pinouts)

### 3. GPIO模式不能靠取消一行注释修复

脚本没有显式调用 `GPIO.setmode()`，但不能因此判定必然启动失败：官方Blinka的Nano路径在导入时可以设置 `GPIO.TEGRA_SOC`。`SPI1_MOSI`是SOC字符串名称。直接取消 `GPIO.setmode(GPIO.BOARD)` 注释，既可能与已有模式冲突，也不能继续把字符串当作BOARD物理编号。

本次没有改这一段，实际安装版本尚未逐项核对。以后遇到编号或载板兼容报错，先保存完整异常、查看实际库与当前mode，再对照Rev2载板针脚；不以“Carrier board is not from a Jetson Developer Kit”警告单独判断全部控制失败，也不忽略它在接线验证中的意义。[Blinka Nano GPIO源码](https://github.com/adafruit/Adafruit_Blinka/blob/main/src/adafruit_blinka/microcontroller/tegra/t210/pin.py)、[NVIDIA模式定义](https://github.com/NVIDIA/jetson-gpio)

### 4. 后续改进代码时，优先解决可诊断性和退出行为

这些是后续建议，**今天没有修改部署**：

- 把初始化角度和每个通道的机械允许范围做成明确配置；接机构前重新审查170°/30°和各预设动作。
- 输入处理改为严格匹配命令前缀，并分别处理解析错误、范围错误和硬件异常。现有 `'a' in str`、`'b' in str`及宽泛 `except`可能误把I²C异常打印成输入格式问题。
- 明确停止策略：退出是保持当前位置、回安全角度、停止PWM还是关闭电源，需要按机构设计决定；不能把“Ctrl+C”一概等同于立即断驱动。
- 目前 `input()`在ROS Timer回调里阻塞等待，0.5秒不是保证每半秒处理一条指令的实时周期；手动输入和ROS消息回调可能分别写同一通道。以后考虑单一指令队列、互斥与超时处理。[ROS Timer源码](https://github.com/ros/ros_comm/blob/melodic-devel/clients/rospy/src/rospy/timer.py)
- 测试时查询 `/gpio_cmd` 的发布者，避免其他任务节点同时下发动作；先看 `rostopic info /gpio_cmd`，记录Publisher与消息来源，不在未核对机构时发送Drop／PUT动作。
